1 · Foundations: what problem is this even solving?

Before any command, understand why version control exists. If you get the mental model, everything else is just vocabulary.

The problem, without version control

Imagine a team writing code (or any file) with no tooling. You quickly hit four pains:

  • The “final_v2_REALLYfinal” mess — copies everywhere, and nobody knows which is the real one.
  • Overwrites — two people edit the same file; one save destroys the other’s work.
  • “It worked yesterday” — something broke and there’s no way to go back to a known-good state.
  • No memory — no record of who changed what, and above all why.
DefinitionVersion control is a system that records changes to a set of files over time so you can recall specific versions later. [1] Think of it as three tools in one: a time machine (restore any past state), a logbook (who/what/why), and a merge machine (combine parallel work safely).

Git vs GitHub — not the same thing

This trips up every beginner, so nail it now:

Git = the tool
A free, open-source program that runs on your computer and does the version control. Works offline. Created by Linus Torvalds. It knows nothing about the internet by itself.
GitHub = the platform
A website that hosts Git repositories in the cloud and adds collaboration on top: pull requests, code review, issues, automation (CI), permissions. It’s where the team meets around the code.

Analogy: Git is the engine; GitHub is the dealership + garage + meeting room built around it. Alternatives to GitHub exist (GitLab, Bitbucket) and Git works with all of them.

Two ideas that make Git click

1. It’s distributed

When you clone a repository you download its entire history, not just the latest files. [2] Every clone is a full backup.

Why it mattersYou can work fully offline, commit as much as you want locally, and if the server dies, any clone can restore it. There’s no single point of failure. [1]

2. It stores snapshots, not differences

Every time you save (a commit), Git takes a picture of what all your files look like at that moment (unchanged files are just referenced, to save space). [2]

Why it mattersYou reason about whole states of the project (“go back to this snapshot”) instead of juggling a pile of patches.

Your internet is down. Can you still commit your work with Git?

Git lives on your machine with the full history. You commit offline all day; you only need the network to push/pull. [1][2]

2 · How Git thinks (the model to internalize)

This is the thing to remember. Get this and the commands stop being magic. [2]

The three areas + the remote

Your work moves through four places:

Working directorythe files you edit
→git add
Staging areathe “index”: next commit’s draft
→git commit
Local repo.git : saved snapshots
→git push
Remote (GitHub)shared copy

And it flows back: git fetch/git pull bring the remote’s new commits down into your local repo and working directory.

Correspondingly, a file is always in one of three states: modified (changed but not staged), staged (marked for the next commit), or committed (safely stored). [2]

Why a staging area at all?It lets you craft each commit deliberately — stage only the changes that belong together, leave the rest for the next commit. That’s how you get clean, logical history instead of one giant “did stuff” blob. [3]

What a commit really is

A commit = a snapshot + metadata: author, date, a message, a unique hash, and a pointer to its parent commit(s). Commits are immutable — the hash is the content.

Why messages matterThe diff already shows what changed. The message exists to explain why. Six months later, that “why” is the difference between understanding a change and fearing it.

Branches & HEAD

A branch is just a lightweight, movable pointer to a commit. Creating one is instant and cheap. [4] HEAD points to the branch you’re currently on.

# main has commits A-B-C. You branch off and add D, E:

  A---B---C        main
           \
            D---E   feature  (HEAD here)
Why branch?To isolate a piece of work so main stays stable and deployable, and so several people work in parallel without stepping on each other. Branching is the whole basis of team workflows.

Merging brings branches back together

  A---B---C-------F   main   (F = merge commit)
           \     /
            D---E      feature
  • Fast-forward: if main didn’t move, its pointer just slides forward to your commits. No merge commit needed.
  • Merge commit: if both branches moved, Git creates a new commit (F) with two parents, joining the histories.

Remotes: origin & upstream

  • origin — the default name for your main remote (your GitHub copy).
  • upstream — the conventional name for the original repo you forked from (open-source flow).
  • git fetch downloads new data but changes nothing in your files; git pull = fetch + merge.

You edited 3 files but only want 1 in your next commit. What does the staging area let you do?

Staging exists precisely so you assemble a commit deliberately: git add the changes that belong together and commit those. [2][3]

3 · A day in the life: the loop you’ll repeat forever

This is what “working on GitHub” actually looks like, hour to hour. Learn this loop and you can function on almost any team.

One-time setup

# Copy the repo (with full history) to your machine, once:
git clone https://github.com/org/repo.git
cd repo

The loop, step by step

  1. Start from the latest. git switch main && git pull
    Why: never build on stale code; fewer conflicts later.
  2. Create a branch for the task. git switch -c feat/login-form
    One task = one branch. main stays clean.
  3. Do the work. Edit files. Run the app / tests locally.
  4. Inspect before saving. git status (what changed), git diff (the actual lines).
    Habit of good engineers: look before you commit.
  5. Stage what belongs together. git add file.js (or git add -p to pick pieces).
  6. Commit small & often. git commit -m "feat: validate login form"
  7. Repeat 3–6 as the work grows.
  8. Push the branch to GitHub. git push -u origin feat/login-form
  9. Open a Pull Request on GitHub (details in tab 4).
  10. Address review: push more commits; discussion lives in the PR.
  11. Merge after approval + green checks.
  12. Clean up. git switch main && git pull && git branch -d feat/login-form

A realistic terminal session

git switch main
git pull                       # get teammates' merged work
git switch -c feat/us-201-signals

# ...edit code...
git status                     # see what changed
git diff                       # review the exact lines
git add force-app/main/default/classes/SimuladorClient.cls
git commit -m "feat(US-201): add SimuladorClient to page /telemetry"

git push -u origin feat/us-201-signals
# -> GitHub prints a link to open the Pull Request

Your three instruments

  • git status — where is everything? (modified / staged / clean) [6]
  • git diff — what exactly did I change? [6]
  • git log --oneline --graph — the history as a picture.
Why small commits & short branches?Small commits are easy to review, easy to revert one-by-one, and produce a readable history. Short-lived branches merge before they drift far from main, which means fewer and smaller conflicts. Big branches are where projects get stuck.

What’s the very first thing to do before starting a new task?

Always start from an up-to-date main. Branching off stale code guarantees painful conflicts later. [7]

4 · Collaboration: the GitHub platform

Git handles history. GitHub is where a team turns that into a process: issues, pull requests, review, and permissions.

The building blocks

  • Repository — the home of the project: code, history, issues, PRs, settings. Public or private.
  • README — the front page: what the project is, why it exists, how to run it. First thing anyone reads.
  • Issues — trackable units of work (bugs, features, tasks) with title, description, labels, assignees, milestones. [16]
Why issues?They give the team one searchable backlog and a place to discuss before code is written. Linking a PR to an issue with a keyword (Closes #123) auto-closes the issue on merge — full traceability from idea → code. [16]

Pull Requests — the heart of it

A Pull Request proposes merging your branch into another (usually main). It’s the checkpoint before code reaches the trunk. [8]

Anatomy of a PR:

  • The diff — every change, reviewable line by line.
  • The conversation — general and line-level comments.
  • Commits — the history of the branch.
  • Checks — automated CI results (tests, lint) shown right there.
  • Reviewers — who must approve / requested changes.

Not ready yet but want early eyes? Open it as a draft PR. [8]

Why PRs instead of pushing to main?A PR is a gate: review catches bugs, CI proves it still works, and the discussion becomes a durable record of why the change was made. It also stops half-finished work from breaking everyone else.

Code review — the highest-leverage habit

Giving a review
Understand the intent first. Check correctness, readability, tests, edge cases, security. Comment specifically and kindly. Separate blockers from nits (“nit:”). Suggest, don’t command. Approve when it’s good enough, not perfect.
Receiving a review
It’s about the code, not you. Respond to every comment, push fixes, ask when unclear, then re-request review. New pushes after an approval dismiss it. [7]
Why review is worth the timeIt catches bugs early (cheapest place to fix them), spreads knowledge so no one is a single point of failure, keeps the codebase consistent, and creates collective ownership. It’s the single most effective quality practice a team has.

Two collaboration models

ModelHow it worksUsed when
Shared repo (branch)Everyone has write access, clones the same repo, works on branches, opens PRs.Company/team repos. This is what Nova Casa uses.
Fork & PRYou fork (your own copy), clone your fork, push there, and open a PR to the original (upstream). Maintainers merge. [12]Open source / no write access to the original.

In the fork model, origin is your fork and upstream is the original; you periodically sync your fork with upstream. [12]

Why link a PR to an issue with “Closes #42”?

Keyword links tie code to the work it resolves and auto-close the issue on merge. [16]

5 · Merging, conflicts & undoing things

Where beginners get scared — unnecessarily. Conflicts are normal and safe once you understand them.

Three merge methods on GitHub

MethodWhat it doesBest when
Merge commitKeeps every commit and adds a merge commit (two parents).You want the complete branch history.
Squash & mergeCombines all the PR’s commits into one commit on main.A PR = one logical change with messy fixups. Nova Casa uses this.
Rebase & mergeReplays each commit onto main individually, no merge commit → linear history.Commits are already clean and you want a straight line.

All three are documented by GitHub. [9] Caveat: after a squash-merge, don’t keep working on the same branch — you’ll re-introduce already-squashed commits and hit the same conflicts repeatedly. Start a fresh branch. [10]

Merge conflicts: what & how

A conflict happens when two branches change the same lines of a file (or one edits a file the other deletes). Git can’t guess your intent, so it asks you. [11] It marks the spot:

<<<<<<< HEAD
timeout = 30;        # your branch's version
=======
timeout = 60;        # the other branch's version
>>>>>>> main

You choose or blend, delete the <<< / === / >>> markers, then git add and commit. Simple conflicts can be solved in GitHub’s web editor; complex ones on the command line. [11]

How to avoid most conflictsKeep PRs small, pull/merge main into your branch often, and coordinate when several people must touch the same file.

Rebase vs merge (the philosophy)

  • Merge preserves history exactly as it happened (with merge commits).
  • Rebase rewrites your branch’s commits to sit on top of the latest main → a clean, linear history. [5]
The golden rule of rebasingNever rebase commits others have already pulled (shared/public history). Rebase only your local, un-pushed work. Rewriting shared history breaks everyone else’s repo. [5]

Undoing things (your safety net)

CommandUse it to…Safe on shared history?
git restore <file>Throw away un-committed changes in a file.Local only
git revert <commit>Make a new commit that undoes an old one.✅ Yes
git resetMove the branch pointer back; --hard can delete work.⚠ Careful, local
git stashShelve changes temporarily to switch tasks.Local only

git reset --hard can lose work — understand it before using it. [6] For anything already pushed, prefer git revert.

You need to undo a commit that’s already on main and pulled by teammates. Best tool?

revert is safe on shared history; reset --hard and rebasing rewrite history others depend on. [5][6]

6 · What makes it professional

The conventions and automation that separate a hobby repo from a team-grade one.

Commit message conventions

The de-facto standard is Conventional Commits [18]: type(scope): subject with types like feat, fix, docs, refactor, test, chore, ci.

✗ Don’t
update stuff
fixed it.
asdf
✓ Do
feat(US-201): add SimuladorClient

Why: subscriber needs paged ingestion.
Refs: T4.1
Why a convention?Consistent prefixes make history scannable and enable automatic changelogs and versioning. Subject in the imperative, no trailing period; the body explains the why. (This repo’s exact rules + the commit-msg hook live in CONTRIBUTING.md.)

.gitignore & secrets

  • Keep build artifacts, dependencies, and IDE files out of git with .gitignore.
  • Never commit tokens, passwords, keys, or production data. Use env vars / secret managers.
  • Turn on secret scanning + push protection so GitHub blocks accidental secret pushes. [14]

Tags, releases & SemVer

  • A tag marks a point in history (e.g. v1.2.0); a release bundles notes and artifacts around it.
  • Semantic Versioning: MAJOR.MINOR.PATCH — breaking / feature / fix. [17]

CI/CD with GitHub Actions

Continuous Integration = automatically build, test, and lint your code on every push/PR. Continuous Delivery/Deployment = automatically ship it when checks pass. GitHub Actions runs these workflows for you. [15]

Why automate?Humans forget to run tests; machines don’t. CI runs the same checks, the same way, for everyone, on every change — and blocks the merge if something breaks. It turns “I think it works” into “the pipeline proves it works.”

Branch protection

Rules on main that enforce the workflow: no direct pushes, require a PR, require approvals, require green status checks, block force-pushes. [13]

What’s the point of running CI on every pull request?

CI runs the same checks for everyone on every change and blocks merges when they fail. [15]

7 · Translating all this to Salesforce

Everything above still applies — but Salesforce adds one twist that changes the whole game. Understand the twist and the rest follows.

The one big ideaIn “normal” software, the repo IS the application — running it just executes those files. In Salesforce, the running application lives in an org: a live, shared, mutable database + metadata in Salesforce’s cloud, separate from your files. Git versions the files; the org has its own current state. Bridging that gap is the entire challenge.

Metadata is your source

Everything you build — Apex classes, LWC, objects, fields, flows, permission sets — is represented as metadata: XML + code files in a Salesforce DX project. That is what lives in git. [19]

Two ways to change things → drift

You can change the org by clicking in Setup (changes the org, not git) or by editing files (changes git, not the org until you deploy). If you only click, the next deploy doesn’t know about it and can erase it.

RuleThe repo is the source of truth. Anything you build by clicking must be retrieved into your branch the same day, or it’s lost. [21]

Deploy & retrieve = the bridge

Local filesforce-app/ in git
→deploy
The orglive app
←retrieve
Local filescapture Setup clicks
  • Deploy (sf project deploy start) pushes your metadata into an org — the SF equivalent of “apply my code to this environment.”
  • Retrieve (sf project retrieve start) pulls metadata from an org into your files — use it to capture Setup clicks.
  • Validate first with --dry-run: a check-only deploy that also runs tests but changes nothing.
Careful: “deploy” ≠ “git push”git push uploads commits to GitHub. deploy pushes metadata into a live org. They’re different actions to different places — you do both.

Why the org makes teamwork harder: “last deploy wins”

Git merges parallel work intelligently. An org does not: a deploy simply overwrites the component with your version. So even with perfect git history, two people deploying to the same shared org can clobber each other.

This is exactly why Nova Casa’s deploy rules existFrom a branch, deploy only your story’s files; deploy the full force-app only from main; coordinate shared files (permission sets, layouts, Case) in Slack. Git protects history; discipline protects the shared org.

Environments (map them to the git mindset)

EnvironmentWhat it isUse for
ProductionThe real org: real users & data.Never develop here.
SandboxA long-lived copy of production (varying data). [22]Org Development model; testing/UAT.
Scratch orgAn empty, disposable org created from your project config via CLI; spun up per feature, thrown away. [20]Source-driven dev & CI — like a fresh clean environment per branch.

Two development models

  • Org Development Model — work against sandboxes/DE/production without source tracking; retrieve/deploy metadata explicitly; align the repo to the org. Simpler; effectively what Nova Casa does with a shared dev org. [19]
  • Package Development Model — organize metadata into versioned packages, develop against source-tracked scratch orgs, lean on CI/CD. More modular and scalable. [20]

Source tracking: in source-tracked orgs the CLI knows the diff between org and local, so you push/pull; in non-tracked orgs you deploy/retrieve. [20]

The testing gate becomes deployment law

Green tests aren’t just nice — they’re the door to production.Salesforce requires at least 75% Apex coverage with all tests passing to deploy to production. [28] A validation deploy runs those tests without saving anything.

CI/CD for Salesforce (GitHub Actions, translated)

On each PR, a pipeline can: spin a scratch org (or run a check-only validation against a sandbox), deploy the metadata, run Apex tests + LWC Jest + PMD/Code Analyzer, and report status back to the PR. Merge only if green. On merge to main, deploy to the next environment. DevOps Center is Salesforce’s own UI for this — it makes git the source of truth and manages the pipeline so admins (clicks) and devs (code) share one flow. [19]

The Salesforce daily loop

  1. git switch main && git pull
  2. Create a branch for the story.
  3. Make changes in code and/or in a dev/scratch org.
  4. Retrieve any Setup clicks into the branch so they’re versioned.
  5. Validate a deploy (--dry-run) of just your files; run tests.
  6. Commit, push, open a PR.
  7. CI validates + tests; a teammate reviews.
  8. Squash-merge.
  9. Author deploys the full force-app from main to the shared org; delete the branch.
Engineering standards inside the code (Apex / SOQL / triggers / security / LWC) deep dive

Apex — bulkification (non-negotiable)

Apex runs multitenant with strict governor limits. Always process collections; triggers handle up to 200 records per batch. Never put SOQL/DML in a loop — collect IDs in a Set, query once, DML once. [24] Key sync limits: 100 SOQL, 50k rows, 150 DML, 10k ms CPU. [23]

Triggers — one per object + handler

One trigger per object (order isn’t guaranteed otherwise); the trigger body delegates to a handler class with a method per context; add recursion guards. [25]

Security — CRUD/FLS/sharing

API 67.0 runs Apex in user mode by default. Declare sharing explicitly; use WITH USER_MODE on SOQL/DML and Security.stripInaccessible() for graceful degradation; never concatenate user input into SOQL. [26][27]

Testing

Cover positive, negative, bulk (200) and exception paths with Assert; create data before Test.startTest(); isolate data (avoid SeeAllData=true); use System.runAs(). 75% is the floor, not the goal. [28][29][30]

LWC

Prefer LDS / UI API (caches + enforces security, no Apex); mark Apex @AuraEnabled(cacheable=true) only on reads; fetch only the fields you render; paginate; keep LWS on and lint. [31]

Static analysis

Run Salesforce Code Analyzer (PMD): ApexCRUDViolation, ApexSOQLInjection, AvoidLogicInTrigger, and more. [32]

You git push your branch. Is your change now live in the Salesforce org?

The org is separate from git. git push shares code with the team; sf project deploy start applies it to an org. [19]

Daily checklist (GitHub + Salesforce)

Tick items off — progress is saved in your browser.

  • Started from an up-to-date main (git pull) before branching.
  • One short branch for this task; type/scope-description name.
  • Small commits with Conventional-Commit messages that explain the why.
  • Ran git status/git diff before committing; no secrets staged.
  • Opened a focused PR with a clear description and how to test it.
  • CI is green; a teammate reviewed and approved.
  • SF: retrieved any Setup clicks into the branch (nothing lives only in the org).
  • SF: validated with --dry-run and deployed only this story’s files from the branch.
  • SF: Apex bulkified, one-trigger-per-object, WITH USER_MODE, tests ≥ 75% and passing.
  • After merge: pulled main, deployed full force-app from main, deleted the branch.
