# Decisions and risks (ADR-lite)

Discovery deliverable 6 ("Decisiones y riesgos"), which is still updated in Development. It is the only place that explains why: the other documents cite the decision number instead of repeating the reason. Every non-obvious decision is logged here with its dropped alternative and the trade-off, so that nobody — human or AI — reverts it without realizing why it was made.

Don't confuse this with the "Acuerdos" section of `Sprint 2 - Nova Casa.md` (MDSS verbatim): those are the agreements **already closed** by the brief/facilitator, and they aren't contradicted without documenting and testing them here again. This file is where the pair **proposes and logs its own decisions** within those limits.

## How to add an entry

Copy this template, use the next free number, keep the entries in numerical order and keep the status up to date.

```markdown
## D00X — <short title>

- **Status**: Proposed | Accepted | Rejected | Superseded by D0YY
- **Date**:
- **Context**: what problem or ambiguity forces a decision?
- **Decision**: what gets done.
- **Alternative dropped**: what other option was considered.
- **Trade-off**: what the chosen decision gains and what it gives up.
- **Risk / dependency**: what could invalidate this and what it depends on.
- **Test criteria**: which test fails if the decision stops being met.
- **Next action**: what is still needed to validate or implement it.
```

Statuses: **Proposed** means the pair made the decision (many are already on `main` and in the org) but a confirmation is still missing, from the facilitator or from the other team member; the Status line says which. **Accepted** means the pair considers it closed. John and Juan Diego decide when an entry moves from Proposed to Accepted.

## D001 — Intervention object: Case

- **Status**: Accepted
- **Date**: 2026-09-29
- **Context**: BR-205/BR-206 require a critical signal to produce an operational intervention that the maintenance coordinator can review and follow up on. The MDSS agreement ("Incidente") requires the behavior (at most one intervention per unique critical message) but doesn't fix the Salesforce object that represents it. `CONTRIBUTING.md` already named `Case` as a shared file and talked about "cases" created by ingestion before this decision was logged here.
- **Decision**: the intervention is modeled as `Case` (standard object).
- **Alternative dropped**: `Work Order`.
- **Trade-off**: `Case` comes enabled in the org with no extra configuration and reuses processes, permissions, queues and list views the team already knows. It gives up the maintenance-specific fields of `Work Order` (Work Type, Service Appointment), which also require Field Service — they aren't part of the sprint's base scope and aren't worth the cost of enabling and licensing Field Service just for this.
- **Risk / dependency**: if a later phase needs to schedule technician visits or assign field resources, this decision may need to be reopened and Field Service evaluated.
- **Next action**: none to close the decision; when implementing BR-205/BR-206, check whether `Case` needs custom fields (severity, related asset, message key) and document them in the data model.

## D002 — Name of the simulator connection components (HP-01)

- **Context**: backlog task T1.1 specified creating the External Credential as `Nova_Casa_Simulator_Auth`. Keeping the current name avoids that risk; the cost is that the original backlog (T1.1) stays out of line with reality until it is corrected there.

## D003 — `occurredAt` tie: highest severity wins, then `messageId`

- **Status**: Accepted
- **Date**: 2026-10-01
- **Context**: the Discovery agreement leaves open the rule for when two valid signals for the same `asset`+`measurement.type` arrive with the same `occurredAt` — it requires the rule to be deterministic and forbids arrival order from deciding.
- **Decision**: the reading with the highest resulting severity wins (compared against `Umbral__c` the same way as in normal classification, using the same numeric level that already feeds `Severidad_Nivel__c`). If severity also ties, `messageId` is used as the second criterion, in ascending alphabetical order (purely deterministic, with no business meaning).
- **Alternative dropped**: break the tie only by `messageId` without going through severity first — simpler to implement, but it can leave a less severe reading as current when both share a timestamp, which would go against the spirit of "ver la condición más crítica sin ambigüedad" in Laura's problem. Marking the case as `Conflicto` without picking a winner was also dropped: the agreement explicitly asks for a rule that does decide, not one that defers the decision to human review.
- **Trade-off**: the severity rule is more faithful to the product goal, in exchange for depending on severity classification already being resolved in the same processing step (it isn't an independent, isolated criterion the way `messageId` alone would be).
- **Risk / dependency**: depends on the thresholds (`Umbral__c`, see open item below) having real values before this rule can be implemented and tested with concrete cases.
- **Next action**: implement it in the classification logic (Apex, not started yet) and cover it with a test that fails if the tie is resolved by arrival order instead of severity.

## D004 — `Umbral__c` is a custom object, not a Custom Metadata Type

- **Status**: Accepted
- **Date**: 2026-10-01
- **Context**: BR-204 asks for the classification limits to be manageable without redeploying code. Custom Metadata Type (`__mdt`) is the default option for that kind of configuration data, but its records can only be edited from Setup and require the "Customize Application" system permission — admin-only. The sprint agreement is that a non-admin profile (operator/coordinator) can adjust the thresholds without being given admin access.
- **Decision**: `Umbral__c` is modeled as a standard custom object (`__c`), not as a Custom Metadata Type. Edit access is controlled with FLS/permission set on the object, like any other operational data.
- **Alternative dropped**: `Umbral__mdt` (Custom Metadata Type).
- **Trade-off**: it gains the ability to give edit access to a non-admin profile without touching "Customize Application"; it gives up what CMDT provides for free (records travel as metadata and deploy on their own between environments, with no Data Loader or data scripts).
- **Risk / dependency**: none functional. The permission set that grants access to `Umbral__c` still has to be defined (see D005/BR-208) so that non-admin editing is real and not just theoretical.
- **Next action**: when defining the operator/coordinator permission set (D005), include CRUD/FLS on `Umbral__c` for the profile that must be able to adjust the limits.

- **Trade-off**: it reuses standard Salesforce sharing and metadata, in exchange for stretching the usual meaning of `Account`.

The OWD change is hard to revert — it needs its own PR, agreement from John and Juan Diego, a deploy only from `main` (`CONTRIBUTING.md` rule), and approval from the MDSS facilitator because it touches BR-208. Only the identity field is brought forward here, because it is low risk and reversible on its own.

## D006 — Seeding `Umbral__c` from the catalog load (HP-04)

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: T3.2 asks for a threshold for each combination in the catalog. `Umbral__c` has no external id field, and `/catalog` delivers `thresholdsReference` as ranges (min/max), not as operator + value.
- **Decision**: `CatalogoService.loadCatalog()` seeds `Umbral__c` with the team's reference table (T2.7), once for each `asset.type` + `measurement` in the catalog (the unit comes from the catalog). If that combination already has any `Umbral__c` (edited, deactivated or not), nothing is seeded for it.
- **Alternative dropped**: full natural key (type, measurement, severity, operator, value, unit): an edited threshold would stop matching and would be duplicated. An external id field: a model change with no need for it.
- **Trade-off**: it gains idempotency and respect for what the user changed; it gives up having a threshold deleted by hand restored on its own, and new rules aren't added to a combination that is already seeded.
- **Risk / dependency**: operators and values are still "por acordar" (see open item 1 below); the table lives in the code as the initial value, and the operational source is the object.
- **Test criteria**: `CatalogoServiceTest` proves the rule: one threshold per combination (`shouldSeedOneThresholdSetPerCombination_WhenCatalogIsValid`), reloading doesn't duplicate (`shouldNotDuplicateThresholds_WhenLoadedTwice`), an edited or deactivated threshold is kept (`shouldKeepEditedThreshold_WhenCatalogIsReloaded`), a partial set isn't completed (`shouldNotCompletePartialSet_WhenCatalogIsReloaded`) and a user without access to `Umbral__c` gets a wrapped `CatalogoServiceException` (`shouldThrowException_WhenRunningAsUserWithoutUmbralAccess`).
- **Note**: seeding these operators and values means the team has already chosen them in practice; they are still pending confirmation from the facilitator.
- **Next action**: confirm operators and values with the facilitator.

## D007 — Signal age is flagged with a display parameter (`staleMinutes`), not with a threshold

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: BR-207 asks for the operator to recognize the age of the information. The screen needs a cutoff to flag a signal as "desactualizada". The "Umbrales fuera del código" agreement covers the severity classification limits (D004), not this cutoff.
- **Decision**: the cutoff is a design property of the LWC (`staleMinutes`, 15 by default), editable in Lightning App Builder for App and Home pages. It only decides whether the "(desactualizada)" mark is shown; it has no influence on severity or on any server decision. The default value lives in a single JS constant, with the same value in `js-meta.xml`.
- **Alternative dropped**: a value per asset type or measurement in `Umbral__c` or Custom Metadata. It adds an object or a deploy, and there is no agreed per-sensor emission cadence to justify it.
- **Trade-off**: it gains a simple screen that can be adjusted without touching code or data; it gives up a different cutoff per sensor type, so a slow sensor can look "desactualizada" without being so. With the Tab placement there is no configuration and the default value applies.
- **Risk / dependency**: if the simulator's real cadence exceeds 15 minutes, there will be false "desactualizada" marks. The value has to be checked against the simulator's emission cadence.
- **Next action**: validate the 15 minutes against the simulator. Test criterion: a signal below the cutoff has no mark, one above it does, and the Tab placement uses the default value.

## D009 — The operator screen assumes valid readings in `Lectura_Vigente__c` and breaks ties by Id

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: the agreement says the asset severity is the highest of its latest valid readings. `Lectura_Vigente__c` has no validity field. Also, D003 breaks ties by highest severity and then by `messageId`, a value this object doesn't store.
- **Decision**: (1) `ActivosOperadorController` assumes that `Lectura_Vigente__c` only contains valid readings: invalid messages are rejected before writing (T2.12), so the screen doesn't validate again. (2) If two readings for the same asset and type tie on `occurredAt` and severity, the highest record Id wins (that is what the controller and its test do), deterministically and without depending on arrival order. It is a read-side safety net: `Clave__c` is unique, so there is normally only one row per key.
- **Alternative dropped**: add a validity field to `Lectura_Vigente__c` or store `messageId` on the reading; it would add data to the model for a case that ingestion already prevents.
- **Trade-off**: a simple screen with no duplicated ingestion logic; it gives up defense in depth if ingestion ever wrote an invalid reading.
- **Risk / dependency**: depends on ingestion really rejecting invalid messages and not writing conflicts to `Lectura_Vigente__c`. If that changes, the screen would show a severity based on an invalid reading.
- **Next action**: confirm that the ingestion tests (T2.12) fail if an invalid reading reaches `Lectura_Vigente__c`.

## D010 — One intervention (`Case`) per unique critical message, idempotent by identity and in system mode

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: BR-205 and the "Incidente" agreement ask for at most one intervention per unique critical message; D001 fixed `Case` as the object. `Case.Identidad_Senal__c` (unique, external id, 60 characters) already exists to prevent two Cases for the same message. We need to decide how the Case is opened in a batch of up to 200 and with which permissions.
- **Decision**: (1) `IntervencionService.abrir` opens one `Case` per identity (`source` + `|` + `messageId`), without consolidating different identities into one open incident. (2) Idempotency by identity: a query looks up existing Cases by `Identidad_Senal__c`; if one exists, the identity points to that Case and nothing is created or updated; an identity repeated within the batch creates a single Case. (3) It runs `without sharing` and with `SYSTEM_MODE` (query and DML) because ingestion runs as Automated Process and doesn't depend on operator/admin permissions; query authorization (BR-208) is a different path. (4) Partial success: a single `Database.insert(..., false)`; each failure is returned by identity in `errorPorIdentidad` without rolling back the other rows. If the failure is `DUPLICATE_VALUE` (another run won the race), it is resolved to the winning Case with an extra query. New Cases get `Origin` = `Telemetria`, `Status` = `En curso`, `Priority` = `Critica`.
- **Alternative dropped**: consolidate several identities into one open incident per asset (extra scope with no decision); `allOrNone` (one bad row would bring down the batch of 200); `with sharing` (ingestion would depend on user permissions).
- **Trade-off**: it gains idempotency guaranteed by the unique constraint and error isolation per row; it gives up one intervention per asset (several different critical signals open several Cases), and system mode skips FLS/CRUD on this path.
- **Risk / dependency**: the caller decides which signal is critical and not late; this service doesn't validate that. The values `Telemetria`, `En curso` and `Critica` live in the repo's versioned standard value sets and must be deployed. Content conflict detection (same identity, different `Huella__c`) belongs to the handler, which must not call `abrir` for a Conflicto, a late signal (Atrasada), a tie-break loser (D003) or a Rechazada signal: `abrir` only receives critical signals that won. `abrir` never compares content and returns the existing Case for a known identity. Risks: the concurrent `DUPLICATE_VALUE` race is handled in code, but no test covers either of its two branches (2026-10-09: no test class mentions `DUPLICATE_VALUE`; in code only `IntervencionService` uses it and, for the log insert, `TelemetriaIngesta`). The branch where the winning Case is found wasn't tested. The branch with no visible winner (the error is reported in `errorPorIdentidad` and the other rows continue) was attempted with a test that deleted the Case and resent the identity, on the hypothesis that a deleted unique value stays reserved; in `nova-cdo` that hypothesis is false: the test failed with an empty error map (the resend didn't produce `DUPLICATE_VALUE`), so it was removed. No injection point was added to the service to force the branch, so it remains untested and would only be reached by a real race.
- **Next action**: test criteria: resending the same identity doesn't create a second Case and returns the existing one; a duplicate identity in the batch creates one; a request with no identity or no `assetId` lands in `errorPorIdentidad` without affecting the others; 200 requests don't consume SOQL/DML per row.

## D011 — The handler persists the log and the current reading, and owns resend, conflict and late-signal detection

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: until now `SenialSensorHandler` only classified in memory. US-201/202/205/206 require logging every message (publishing isn't processing), keeping the latest reading per asset + measurement, and opening one intervention per unique critical message (D010), without letting arrival order decide.
- **Decision**: (1) Persistence order per batch: queries (logs by `Identidad__c`, assets by `External_Id__c`, readings by `Clave__c`), in-memory decision, a single call to `IntervencionService.abrir`, upsert of `Lectura_Vigente__c` by `Clave__c`, final upsert of `Log_Senial__c` by `Identidad__c`; all in `SYSTEM_MODE` with partial success. (2) A row in `Publicada` or `Fallida` (or a missing row) is first processing. An identity already processed with the same `Huella__c` is a resend: only `Reenvios__c` goes up and `Ultimo_Reenvio__c` is set; no state change and no intervention. With a different fingerprint it is `Conflicto`: the log is marked, with no state change and no intervention. The fingerprint is the SHA-256 of the content without `deliveryId` or `publishedAt`. Within a batch, the first event of an identity sets the original fingerprint. (3) Atrasada: a valid reading strictly older (lower `occurredAt`) than the stored current reading, or than the winner of the same batch for the same key, stays in the log as evidence; `Superada`: the one with the same `occurredAt` that loses the D003 tie-break against the current reading or against the batch winner. Neither one overwrites the reading or opens an intervention. Rechazada: invalid data, no threshold, incompatible unit, outside the physical range, or asset outside the catalog. (4) Fallida (T5.16): if the Case for a winning critical signal can't be opened, its log stays `Fallida`, its reading isn't written (the previous current reading stays intact) and the other identities in the batch aren't affected; there is no rollback: if the Case was already created (e.g. the reading upsert failed afterwards), the Case **is not deleted** and stays open; a retry with the same content reuses it because `abrir` returns the existing Case by `Identidad_Senal__c`. The same applies if its reading upsert fails. (5) Content-conflict detection belongs to the handler; `IntervencionService` doesn't compare content and only receives winning critical signals. (6) Hardening: an identity in `Conflicto` doesn't win or open a Case, also within the same batch (the original and the different duplicate are left out of the competition), and no later mark (`Fallida`, `Atrasada`, `Superada`, `Rechazada`) overwrites a `Conflicto`. A resend with another fingerprint on a `Fallida` or `Publicada` row with a stored fingerprint is `Conflicto`, not a silent replacement. `Atrasada` is kept only for what is older than the reading (or than the batch winner); losing the D003 tie-break with the same `occurredAt` is `Superada` (a new value in `Resultado__c`, which must be deployed before the handler). The tie-break compares `occurredAt`, severity, `messageId` and, if they are still tied, the `source`. Identities, assets and keys are compared normalized (upper/lower case, spaces); `Clave__c` uses the catalog's `External_Id__c`. An event whose fields don't fit the target (identity/key 60, `Message_Id__c`/`Source__c` 80, `Delivery_Id__c` 40, `Sensor_Id__c` 50) is rejected with a reason; if the identity exceeds 60 no log row is possible and only in-memory evidence remains. The per-event work and each DML are wrapped in try/catch so that one bad event doesn't discard the 200 in the batch; a failed log upsert leaves a counter and a detail (`fallosDeLog`, `erroresDeLog`). Untrusted text that goes into `Motivo__c` is cleaned (no control characters, max. 255). The class is `without sharing` (BR-208: ingestion doesn't depend on operator permissions).
- **Alternative dropped**: writing the reading first and reverting it if the Case fails (a `Savepoint` would also revert the other identities in the batch); letting `IntervencionService` detect the conflict (it doesn't know the fingerprint or the previous state).
- **Trade-off**: it guarantees there is no critical reading without an intervention and keeps partial success; what it gives up is that, if the winning critical signal fails, the signals in the same batch that it beat stay `Atrasada` (or `Superada` if they tied on `occurredAt`) and the next best one isn't promoted; a `Fallida` row that receives a resend with different content moves to `Conflicto` and is no longer retried by an identical resend; and the resend doesn't refresh `Procesado_At__c`.
- **Risk / dependency**: the log can only vouch for a resend if the row already exists (ingestion inserts it as `Publicada`); the order within the batch decides which event is the original if the same identity arrives twice with different content in the same batch. A row that is already `Procesada` and receives a conflict moves to `Conflicto` and keeps `Caso__c`. Implemented with tests in `SenialSensorHandlerTest`; deployed to `nova-cdo` and tested with `sf apex run test`: 34 of 34, 97 % coverage of the handler and 100 % of the trigger.
- **Known limits (accepted by the pair)**: (a) an event without `source` or `messageId`, or with an identity longer than 60 characters, leaves no persistent evidence: only transaction counters and maps (`senialesSinIdentidad`, `rechazadasSinLog`). (b) `Duplicada` is still in the `Resultado__c` picklist but the handler never writes it (reserved): the resend is recorded with `Reenvios__c` and `Ultimo_Reenvio__c`, without changing `Resultado__c`. (c) It departs from the `Resultado__c` values in the prototype `entregables/03-arquitectura-flujo-datos.html` (Procesada · Duplicada · Atrasada · Invalida · Publicacion rechazada): the handler uses Publicada, Procesada, Rechazada, Atrasada, Superada, Conflicto and Fallida; the prototype guides the design but isn't the spec. (d) If the `source` contains `|`, `desdeVigente` splits the stored identity (`source|messageId`) wrongly and the D003 tie-break against the current reading may compare the wrong `messageId`; the simulator doesn't use `|` in `source`. (e) `Lectura_Vigente__c.Unidad__c` and `Log_Senial__c.Message_Type__c` are restricted picklists without a length of their own. `Message_Type__c` is validated against the picklist values (`Schema` describe, no SOQL/DML): a non-empty value outside it stays `Rechazada` with a reason that names the field, isn't copied to the log row, doesn't write a reading and doesn't open a Case; an empty value behaves as before. For `Unit__c` the handler only rejects values longer than 255 characters: a short value outside the picklist isn't validated and would make that row's upsert fail (it ends up in `fallosDeLog`). (f) Salesforce's `Occurred_At__c` doesn't store milliseconds: the handler truncates `occurredAt` to seconds when it reads the event, so the comparison with the stored current reading uses the same precision and the D003 tie isn't decided by arrival order; two signals that differ only in milliseconds count as the same `occurredAt`. (g) If processing an event fails at the decision stage, its `Fallida` row carries `Source__c`, `Message_Id__c`, `Occurred_At__c` and `Procesado_At__c` (the first two are required); `Huella__c` isn't written, so the original isn't overwritten. (h) A signal with a lower `occurredAt` than the winner of the same batch, for the same asset and measurement type, stays `Atrasada` (reason "Más antigua que ... (el lote)"), just like one older than the current reading: it's kept as evidence, doesn't overwrite the reading and doesn't open a Case even if it's critical. Decided by John on 2026-10-05 after the `QA_200` run (167 of 189 rows ended up this way). Marking them `Superada` was dropped; that value stays reserved for the D003 tie. **The MDSS facilitator hasn't confirmed it**: it's still open with Juan Diego and with the facilitator (see "Batch dependence" in `evidencia-escenarios.md`), and if the answer changes the scenario runs have to be redone. Since 2026-10-09 it is pinned by `SenialSensorHandlerTest.unaCriticaMasViejaEnElMismoLoteQuedaAtrasadaYSoloLaMasNuevaAbreCase` and `...AunqueLlegueDespuesDeLaNueva` (the older one stays `Atrasada` without a Case and the newer one wins, in both batch orders); `unaLecturaMasNuevaActualizaValorUnidadFechaYSeveridadDeLaMismaFila` checks that a newer reading rewrites the value, unit, date and severity of the same row. The comment before them says they pin the current behavior on purpose and that, if the policy changes, they have to be changed together with the handler. It's a batch-level interpretation of "atrasada" that departs from the letter of the agreement (a late signal is one that arrives after a newer one): a unique critical signal that arrived first in the batch doesn't open an intervention, and whether it opens a Case depends on how the stream is split into batches. If the facilitator rejects it, the baseline is one intervention per unique critical message regardless of batch order (BR-205). The log already tells the two causes apart: the `Motivo__c` of the batch case says "(el lote)" and the one for a signal older than the current reading doesn't.
- **Next action**: test criteria: an identical resend doesn't change the reading or the Case and increments `Reenvios__c`; the same identity with another value stays `Conflicto` with no changes; an older signal stays `Atrasada` without touching the reading or opening a Case; an `occurredAt` tie is decided by D003 regardless of order and the loser stays `Superada` (not `Atrasada`); a Case that fails leaves `Fallida` and no reading while another identity in the batch does get processed; 200 events use a fixed number of SOQL/DML.

## D012 — The operator screen goes back to the low-fidelity prototype

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: D008 (point 1) replaced the prototype's look with `lightning-card` cards with SLDS badges and icons. ## D013 — Ingestion as a Queueable chain, 'Publicada' log before the event, and what happens to what doesn't fit or doesn't get published

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: US-201 needs to fetch `/telemetry` page by page (simulator cursor), record "publicada" separately from "procesada", and publish `Senial_Sensor__e`. The MDSS contract doesn't cover opening the session or the `X-Simulator-Cursor` header (see `docs/contrato-mensaje.md`), nor what to do if an event can't be published or a value doesn't fit in the field.
- **Decision**:
  1. `TelemetriaIngesta` is a Queueable chain, one job per page: callouts first (`POST /session` only in the first job, then `GET /telemetry`), then DML (insert of `Log_Senial__c` as `Publicada`, `EventBus.publish`, update), and finally enqueuing the next one. There is never a callout after a DML in the same transaction. The chain stops on `hasMore=false`, an empty page, the page cap (25 by default, 100 maximum) or exhausted queue depth.
  1.bis. **Correction 2026-10-05**: in a real run (`DUPLICATES`) the chain didn't stop with the expected `WARN`: `AsyncInfo.hasMaxStackDepth()` returned `false` one job too late and the sixth job (depth 5) ended `Failed` with `Maximum stack depth has been reached` (uncaught exception), losing the rest of the ingestion. Fix in `TelemetriaIngesta`: (a) enqueuing the next job asks the platform for a greater depth with `System.enqueueJob(siguiente, opciones)` and `AsyncOptions.MaximumQueueableStackDepth = 30` (`PROFUNDIDAD_COLA_SOLICITADA`); (b) our own fallback, independent of what the platform reports, stops the chain at `pagina >= 27` (`PROFUNDIDAD_LOCAL_MAXIMA`) with the same usual `WARN`, never with an uncaught failure. 27 sits above the default cap (25) on purpose: a run without an explicit `maxPaginas` must not be stopped by this fallback. It hasn't been empirically validated that the platform honors a depth of 30 in `nova-cdo` (it is a trial/developer org); if a future run asks for more than 27 pages and the platform really has a ceiling below 30, the same failure could happen again and both numbers would have to be raised or the mechanism changed (for example, resuming with Scheduled Apex, which opens a new async context). Pending confirmation with a real run that asks for more than 27 pages.
  2. The cursor travels only as private state of the next job: it isn't written to records, logs, exception messages or fixtures. The client's exception messages carry only the operation, the HTTP code or the exception type name, never the body or the original message (a `JSONException` or a `CalloutException` can quote the body or the request).
  3. Nothing is discarded silently (BR-202, BR-209). Each discard leaves a `Log_Senial__c` row with `Resultado__c = 'Rechazada'` and `Motivo__c`: messages without `source` or `messageId`, with a `source` or `messageId` longer than 80 characters or with a `source|messageId` identity longer than 60, and `data` elements that aren't objects (position and page in the reason). Since the real identity doesn't fit or doesn't exist, the row key is a hash (`ID-LARGA|...`, `SIN-ID|...`, `DESCARTE|...`): the same repeated message lands on the same row. These messages aren't published. `Source__c` and `Message_Id__c` are stored truncated to the field length; the content of an element that isn't an object is never stored.
  4. If the log row insert fails for a reason other than a duplicate, the event isn't published (an event without a row would be untraceable) and it shows up in the `logsFallidos` and `noPublicadosPorLog` counters and in a `WARN` line from the job (numbers only). There is no row to prove it, because the insert failed; that is the minimum record and it stays open (see below).
  5. If `EventBus.publish` fails for an event, the row this run created moves to `Fallida` with the status code in `Motivo__c`. A resend (identity already exists) doesn't touch the row and is published anyway, so the subscriber counts it. The same holds for a `Fallida` row, and for the same message with different content: ingestion doesn't compare content; the handler decides the conflict (same identity, different fingerprint). The handler writes `Huella__c`.
  6. Two events with the same identity on the same page: the first creates the row, the second gets `DUPLICATE_VALUE` inside the same insert and counts as `yaExistentes`. Both are published.
  7. All DML runs `without sharing` and in `SYSTEM_MODE` (ingestion doesn't depend on operator permissions), but the callout isn't independent: the user who calls `iniciar()` (the job runs as that user) needs the `Nova_Casa_Simulator_Integration` permission set, which grants access to the Named Credential's `NovaCasaSimulatorPrincipal` principal. They also need create permission on `Senial_Sensor__e` to publish; that permission set doesn't grant it today (see below).
  8. After a failure mid-chain, the failed job stays visible in Apex Jobs, the earlier pages are already in the log and published, and the chain doesn't continue. The cursor isn't saved for resuming (it would be a secret in data). You run `iniciar()` again: it opens a new session, reads from the start of the scenario, and deduplication by identity means what was already ingested isn't duplicated and doesn't open another intervention; resends are published again and the handler counts them as resends.
  9. Letter case: `Identidad__c` is marked unique (`unique=true`) without an explicit `caseSensitive` in the repo metadata, so the behavior depends on the platform default and hasn't been checked against the org. The handler compares with a lowercase key (`idKey`). Ingestion uses the identity as it arrives. If the field is case-sensitive, two messages that differ only in case would have two log rows but the handler treats them as one identity; if it isn't, the second lands as a duplicate. The field metadata wasn't changed; it remains to be confirmed and, if needed, changed in its own story.
- **Alternative dropped**: a single Queueable that walks all the pages in a loop: it breaks the callout-before-DML order and the per-transaction callout cap. Also dropped: saving the cursor in an object or Custom Setting (secret in data) and truncating long `source`/`messageId` values (it would merge different messages).
- **Trade-off**: each page is its own transaction, so a failure midway leaves the earlier pages already published. Retrying from the start costs rereading pages already ingested, in exchange for not saving the cursor. A failed log insert leaves no row, only counters.
- **Risk / dependency**: the shape of `POST /session` (body `{"scenario": ...}` and response `{"cursor": ...}`) comes from the simulator connection notes (now in `docs/contrato-mensaje.md`) and from the shape of `catalog.json`; it isn't confirmed against the real simulator. In developer/trial orgs the chain stops at depth 5 by default; with the 1.bis correction a greater depth (30) is requested and backed by our own cap (27), but the real ceiling of `nova-cdo` for that request isn't confirmed yet. `Nova_Casa_Simulator_Integration` only grants the credential's principal, not `Create` on `Senial_Sensor__e`: if whoever runs `iniciar()` doesn't have it through another permission set, `EventBus.publish` could fail and the rows would stay `Fallida`; what the platform does with that user hasn't been checked. Permission sets are shared metadata: this is requested from `sf-metadata-dev`, not touched here.
- **Next action**: (a) confirm `POST /session` on the first real run (`QA_200`); (b) open question for `sf-processing-dev`: how the handler treats a row that is `Fallida` due to publishing when the resend arrives (ingestion assumes it is retryable and doesn't touch it); (c) ask `sf-metadata-dev` for `Nova_Casa_Simulator_Integration` (or the ingestion user's permission set) to include `Create` on `Senial_Sensor__e`; (d) check in the org whether `Identidad__c` is case-sensitive; (e) if another branch already uses D013, renumber this entry when integrating (D010 to D012 live on other branches and this branch can't see them).

## D014 — The safe-retry rule is a formula on `Log_Senial__c` (US-209, T6.1)

- **Status**: Accepted
- **Date**: 2026-10-05
- **Context**: BR-209 asks that the Admin see the rejection reason and the processing status, and be able to retry without risk. T6.1 is done when "cada estado dice si se puede reintentar o qué hay que corregir antes". `Reintento_Seguro__c` (checkbox from HP-03) exists, but no process writes it and it is always `false`. Whether a retry is safe depends on how `SenialSensorHandler` treats an identity that is already recorded (D011): a `Publicada` or `Fallida` row with the same fingerprint (or no fingerprint) is processed as if it were the first time; in any other status, the same content is a resend (it increments `Reenvios__c` and sets `Ultimo_Reenvio__c`, without changing `Resultado__c`, the reading or the Case) and different content is `Conflicto`. Retrying means running ingestion again ("Traer señales", D020, or `TelemetriaIngesta.iniciar()`): it rereads the scenario from the start and republishes the events whose identity already exists (D013, points 5 and 8).
- **Decision**: text formula field `Accion_Reintento__c` ("Acción de reintento") on `Log_Senial__c`, calculated from `Resultado__c` and `Reenvios__c`, with no Apex and without touching the handler or ingestion. It shows as a column in the Todas las señales, Fallidas, Rechazadas and Conflictos list views, with read-only FLS in `Nova_Casa_Admin`.

  | `Resultado__c` | `Accion_Reintento__c` | Why |
  |---|---|---|
  | Fallida | Sí: reintentar; la identidad evita duplicar el caso | The handler reprocesses it as the first time. `IntervencionService.abrir` returns the Case that already exists by `Identidad_Senal__c` (D010) and the reading is upserted by `Clave__c`. |
  | Publicada | Sí: volver a publicar el evento | The handler never processed it; the event published again is processed as the first time. |
  | Rechazada | No: corregir el dato en origen y enviarlo con otro messageId (ver Motivo) | With the same identity it isn't reprocessed: the same content only adds to `Reenvios__c` and corrected content ends up `Conflicto`. |
  | Conflicto | No: investigar la huella distinta antes de reintentar | An identity in conflict doesn't win or open a Case (D011, point 6); resending it changes nothing. |
  | Procesada, Duplicada, Atrasada, Superada | No hace falta (with `Reenvios__c` > 0: "No hace falta: el reenvío ya quedó contado") | Final status; a resend only adds to `Reenvios__c`. |
  | Any other value | Revisar | Safety net in case the picklist gains a value and the formula isn't updated. |

  A resend doesn't change `Resultado__c`: it shows as `Reenvios__c` > 0 and in `Ultimo_Reenvio__c`. That's why the "Duplicadas (reenvíos)" list view filters on `Resultado__c = Duplicada` **or** `Reenvios__c > 0`: `Duplicada` is in the picklist, but the handler never writes it (D011, limit b). `Reintento_Seguro__c` is replaced by this formula. It isn't deleted here: deleting a field is a change that's hard to revert and goes in its own PR (`CONTRIBUTING.md`).
- **Alternative dropped**: having `SenialSensorHandler` write `Reintento_Seguro__c` (Apex in John's class, with its own deploy and tests, and a stored value that goes stale if the rule changes), or a record-triggered Flow that calculates it (another automation on a table that ingestion writes in batches of 200, and another copy of the rule). We also don't add a formula checkbox next to the text: the text already starts with "Sí" or "No" and you can filter on that.
- **Trade-off**: the rule is visible, with no code, and is calculated on read, so it doesn't go stale. In exchange, the rule lives in two places: if the statuses the handler reprocesses change, the formula has to be changed by hand.
- **Risk / dependency**: (1) the formula doesn't tell a stuck `Publicada` apart from one the handler will process in seconds; you have to look at `Publicado_At__c`. Retrying it anyway is harmless: if it was already processed, the new event only adds to `Reenvios__c`. (2) The `Rechazada` rows ingestion leaves (no identity or a long identity; keys `SIN-ID|`, `ID-LARGA|`, `DESCARTE|`) are never published: they can only be fixed at the source. (3) A `Fallida` that comes back with a different fingerprint moves to `Conflicto` (D011). (4) `Reintento_Seguro__c` is still on the `Log_Senial__c` layout and in the `Nova_Casa_Admin` and `Nova_Casa_Procesamiento` permission sets.
- **Next action**: decide with John whether to delete `Reintento_Seguro__c` (and remove it from the layout and the permission sets) in its own PR from `main`. The `Log_Senial__c` tab is already in the Nova Casa app (branch `feat/us-209-log-tab`, visible only in `Nova_Casa_Admin`). Test criterion: the query grouped by `Resultado__c` and `Accion_Reintento__c` gives a single text per status (two for the final statuses, depending on `Reenvios__c`) and no "Revisar" row.

## D018 — Save-time validation of contradictory ranges in `Umbral__c` (US-204, T5.10)

- **Status**: Proposed
- **Date**: 2026-10-05
- **Context**: several `Umbral__c` rows share Tipo_Activo + Tipo_Medicion with different severities, and the classifier applies the highest severity that's met. Since threshold editing is open to a non-admin profile (D004), a badly entered range (e.g. Advertencia GT 40 and Crítica GT 35) leaves the Advertencia band unreachable without anything flagging it.
- **Decision**: `UmbralTrigger` (before insert and before update) delegates to `UmbralValidador`, which rejects the save with `addError` when, among active rows with the same Tipo_Activo + Tipo_Medicion + Unidad_Esperada, an Advertencia becomes unreachable because the Crítica covers everything it covers. In the upward direction (GT/GE) the critical limit must be greater than or equal to the warning limit; in the downward direction (LT/LE), less than or equal. With equal limits, the save is rejected if the Crítica has the same operator or is GE/LE (Advertencia GE 40 with Crítica GT 40 is allowed, because the warning still fires at 40). Pairs in different directions and the Inválida severity aren't compared. Contradictions within the same batch are detected too. One query per batch, no DML, `with sharing`.
- **Alternative dropped**: validating in the classifier at ingestion (it would discard signals or silently downgrade them, late and far from whoever made the mistake) or a declarative validation rule (it can't compare against other rows).
- **Trade-off**: the error shows up on save and names both rows; flexibility is lost: changing two limits row by row can fail at the intermediate step (avoided by deactivating a row or saving both in the same batch). With equal limits the rule is stricter than a plain "greater than or equal". Each row gets a single error, the one for the first conflicting row in its group: building a message for every pair exhausted the CPU with 200 contradictory rows (about 20,000 calls); whoever edits a row with several conflicts sees one and, after fixing it, the next.
- **Risk / dependency**: rows that are already contradictory will fail on their next save (the 21 active rows in the org, queried on 2026-10-05, meet the rule). Accepted limitations: (1) it doesn't validate overlapping ranges in opposite directions; (2) it doesn't compare the Inválida: since the classifier evaluates it first, a badly entered Inválida (e.g. GT 10) would reject valid signals, but with an explainable reason in the log (`Rechazada`), not as Normal; (3) it only validates active rows with the same Tipo_Activo + Tipo_Medicion + Unidad_Esperada; (4) the validator's query deliberately doesn't apply FLS, because it needs Severidad, Operador and Valor even if the user has no FLS on them; the error message names the other rows (name, severity, operator and value), so an editor without FLS can read that data through the error. The D019 boundaries are provisional until the facilitator confirms operators and values (D006).
- **Test criteria**: `UmbralValidadorTest` fails if (a) Advertencia GT 40 with Crítica GT 35, or its LT/LE equivalent, is accepted; (b) the reference set seeded by `CatalogoService` is rejected; (c) the GT/GT or GT/GE tie is accepted and GE/GT is rejected; (d) an inactive row, a row with another unit or an Inválida row is compared; (e) a contradiction within the same batch doesn't flag both rows; (f) 200 rows in one DML use more than one query; (g) a row with several conflicting rows gets more than one error, or 200 mutually contradictory rows exceed the CPU limit.

## D023 — Ingestion retries 429/5xx, reopens the session on 409/410 and waits `pollAfterMs` with a Queueable's minimum delay (HP-05, T4.7)

- **Status**: Proposed
- **Date**: 2026-10-06
- **Context**: T4.7 asked for ingestion to withstand a long run: retry on 429/5xx, reopen the session on 409/410 and wait `pollAfterMs` between pages. The simulator contract (`Sprint 2 - Nova Casa.md`) doesn't document those codes; the simulator does send `pollAfterMs` (10000 ms in the samples in `docs/muestras/`) along with `hasMore=true`. Apex can't sleep, and the smallest delay for a Queueable is `MinimumQueueableDelayInMinutes` (whole minutes, 1 to 10).
- **Decision**: (1) On 429 or 5xx, `TelemetriaIngesta` enqueues a new job for the SAME page (same cursor and page number), with a 1-minute delay on the first retry and 2 on the second (`Retry-After` isn't read), up to 3 attempts per page; once they run out, the job fails as before. Callouts come before DML, so a retry never repeats a write. (2) On 409 or 410 when reading the page, it opens a new session only once per page (retries of that page don't reopen it) and reads again; if the read fails again, the job fails. (3) [Superseded by D025: `pollAfterMs` is no longer honored with minute delays] Between pages, the next job is enqueued with `pollAfterMs` rounded up to minutes (minimum 1, cap 10). (4) Every enqueue, retry or next page, counts toward the chain depth (`trabajos`), so D013's local cap also limits retries. Any other error still stops the run.
- **Alternative dropped**: waiting `pollAfterMs` with a loop (it burns the job's CPU and doesn't hit the 10 s precisely), or ignoring it and relying only on the retry on 429 (it can overload the simulator). A `Schedulable` job can't go below one minute either.
- **Trade-off**: a run of N pages takes at least N minutes; `QA_200` (1 page) doesn't change, but a long scenario like `BOUNDARIES` with several pages becomes slow for the demo. Reopening the session restarts the stream from the beginning: messages already published are read again and the log deduplicates them by identity (`source` + `messageId`), but it costs a repeated page of publishing (a resend with the same key doesn't change state or open another intervention).
- **Risk / dependency**: (1) the 409/410 and 429 codes are an assumption, not contract; confirm with the facilitator what the simulator returns when a session expires (T0.2). It also isn't confirmed that a new session repeats the same `source` + `messageId`: if it made up new identities, deduplication wouldn't stop the repetition and the same critical reading could open another intervention (BR-205). (1b) After reopening the session on page N, `pagina` keeps counting from N and the reread is the first page of the new stream, so `maxPaginas` limits the run but not the distinct pages read. (1d) T4.2 (seed and batch size, `iniciar(escenario, semilla, tamanoLote, maxPaginas)`): the reopened session asks for the same seed and the same size only if a seed was given; without a seed it can open a different stream and deduplication by identity doesn't cover it. For a run where repeating the stream matters, pass a seed. The simulator can ignore `batchSize` (`QA_200` returned 200 per page even though 50 was requested), which is why the page `limit` is still the reliable cap (BR-202, maximum 200). (1c) The evidence of retries and reopened sessions is the `reintentos` and `sesionesReabiertas` counters in the summary (a WARN/INFO debug line, with no cursor); if the attempts run out, the job fails and leaves a WARN with that summary, with no `Log_Senial__c` row for that page. (2) The tests don't run in a real chain (see `TelemetriaIngestaTest`): the real `AsyncOptions` delay can only be checked in `nova-cdo` by launching a multi-page run. (3) A failure with no HTTP code (timeout, unreadable body) still has no retry.
- **Test criteria**: `TelemetriaIngestaTest` (a 429 and a 503 enqueue the same page with its cursor and without writing; the last attempt and the depth cap make the job fail; a 409 opens a new session and rereads with the new cursor; a second 410 or a retry of a page already reopened doesn't open another; the second retry waits 2 minutes; [superseded by D025: the next page goes out with the `pollAfterMs` delay and the minute rounding]). They fail if the retry, the reopening or the delay is removed.
- **Next action**: PR owned by John (reviewed by Juan Diego); launch a multi-page run in `nova-cdo` and note how long it takes.

## D025 — The ingestion continues the simulator session across runs (Platform Cache) and one job reads several pages (HP-05)

- **Status**: Proposed
- **Date**: 2026-10-06
- **Context**: verified in `nova-cdo` on 2026-10-06: "Traer señales" always ended with "Terminada · 0 señales registradas". Two causes. (1) `TelemetriaIngesta` chained one Queueable per page and this org stops the chain after 2 jobs (`Ingesta detenida: profundidad maxima de cola alcanzada, paginas=2, recibidos=400, logsCreados=0, yaExistentes=400`), so a run never read more than 400 messages. (2) Every run opened a NEW session (`POST /session`) and the simulator restarts at `msg_000001`, so pages 1 and 2 were always the same 400 messages already stored: all duplicates, no new log row (D013 point 8 had accepted this as a cost). The simulator stream has at least 1600 messages. Read-only probe: simulator cursors are reusable and idempotent (re-reading a cursor gives the same page; an older cursor stays valid after advancing; the `nextCursor` of page 2 continues at `msg_000401..600`); `pollAfterMs` is 10000 but nothing enforced waiting. The MDSS UI keeps ONE session, continues from the saved cursor and only restarts on "Reiniciar sesión".
- **Decision**: (1) The cursor of the next page is kept OUTSIDE any record, in Platform Cache (org partition `NovaCasaSimulador`, class `SesionSimulador`), with a 24 h TTL and a key that is an alphanumeric hash of scenario + seed + batch size (different parameters never share a stream). It is written after the DML of the pages it follows, and ONLY when every message of the run left a complete trace: if any log insert, publish or failed-mark update failed (`logsFallidos`, `noPublicadosPorLog` or `fallosPublicacion` > 0) the previous cursor is kept (`cursorSinAvanzar`), the run stops without a continuation or retry, and the next run re-reads those pages (idempotent by `source` + `messageId`); the same happens if a job fails. When the stream ends (`hasMore=false`) the cursor of the last page read is kept, so the next run polls it again. The cursor is never logged, returned to the client or put in an exception message. (2) One job reads all requested pages in a loop: first ALL the callouts (each page is turned into rows and events in memory at once to release the heap), then ALL the DML (per page: log insert, publish in chunks of 200, update). Reading stops at the page cap, at `hasMore=false`, on an empty page, at 4000 messages per job (log rows + events stay under 10,000 DML rows; a page that could exceed the budget is not started, and count and time are re-checked after every page), at 45 s of reading (wall clock; the platform allows 120 s of callout time and one request may last 60 s) or when heap (50 %), CPU (60 %) or callouts get close to their limit. A job that stops on budget enqueues a continuation (25 pages are 2 jobs, within what this org allows); if the chain is cut, the saved cursor lets the next run continue. The chain remains only for continuation and retries. (3) Retries on 429/5xx and the 409/410 reopen are kept: a failure after some pages were read writes what was read first and retries the page that failed (a non-retryable error at that point does not throw, because that would roll the DML back: it stops the run and leaves `interrumpidaPorEstado` in the summary); 409/410 clears the saved cursor, opens a new session once per page and re-reads, counted in `sesionesReabiertas`. (4) "Reiniciar sesión": `IngestaController.traerSenales(escenario, paginas, reiniciar)` and a checkbox on the screen; `reiniciar` clears the saved cursor AFTER the job is successfully enqueued (so a failed enqueue leaves the session intact; after the `Nova_Casa_Traer_Senales` custom permission check); the 25-page maximum does not change. (5) Without cache (missing partition, no capacity, platform error) the run opens a new session and says so (`cacheNoDisponible` in the summary and on the screen). (6) `estadoIngesta` returns a `detalle` with the counters of the last run (pages, received, `yaExistentes`, session continued / restarted / no cache, end of stream, status that interrupted it), also kept in the cache and never containing the cursor, so "0 señales registradas" is explained by "N ya existían y se omitieron". A summary older than the start of the run being watched is ignored. (7) `pollAfterMs` is no longer honored with minute delays between pages: this supersedes point (3) of the D023 decision (the 1- and 2-minute retry delays stay).
- **Alternative dropped**: keep opening a session per run and raise the page count (the stream restarts at `msg_000001`, so it would re-read the same messages); keep the cursor in a field, Custom Setting or Custom Metadata (secret in data, already ruled out in D013); keep one Queueable per page with `pollAfterMs` delays (the org cuts the chain at depth 2 and every page would cost at least a minute); one job with callouts and DML interleaved (Salesforce forbids a callout after uncommitted DML).
- **Trade-off**: a run continues where the previous one stopped, so it stops repeating messages and 25 pages of 200 fit in 2 jobs; the cost is a new dependency (Platform Cache: a partition with allocated capacity, readable by any Apex in the org's namespace) and hidden state the screen has to explain (hence "Reiniciar sesión" and the detail). Without `pollAfterMs` pages are requested back to back, with no 10 s pause: we rely on the 429 retry and on cursors being idempotent. A non-retryable error mid-run no longer leaves a `Failed` job in Apex Jobs: it shows in the summary and the `WARN`. A restart re-reads from `msg_000001` and everything already stored counts as `yaExistentes`.
- **Risk / dependency**: (1) the Platform Cache capacity of `nova-cdo` is not verified: if the org has none allocated, the partition deploy fails or the code falls back to "new session" and the original defect returns, with the notice on screen; the partition asks for 1 MB (`allocatedCapacity`) and may need adjusting. (2) The simulator may expire a session (409/410 is an assumption, D023): the saved cursor is cleared and a new session opened, with a re-read. (3) The heap, DML and CPU budget of 4000 messages per job was computed, not measured in the org: confirm with a 25-page run and tune `MAX_MENSAJES_POR_TRABAJO`. (4) Platform Cache holds no data in Apex tests, so tests use a map (`SesionSimulador.memoriaDePrueba`) and the real cache path is only checked in the org. (5) If the cache is flushed (platform restart, TTL) the next run silently opens a new session, visible only in the summary. (6) `Pagina.siguienteCursor` is still not filled when `hasMore=false`; if the simulator gave a useful cursor in that case, it could be saved instead of the last one read. (7) If saving the cursor fails (cache full, platform error) the run reports `cacheNoDisponible` and the next run opens a new session, i.e. it re-reads from the start. (8) After a 409/410 reopen, the saved cursor was cleared and a new session started: the next run starts from the new stream's beginning, not from where the old one was. (9) Page numbers are per run (and per job chain), not positions in the stream; they only label the `Rechazada` rows of discarded elements. (10) Replay after a restart relies on an UNCONFIRMED assumption: that a new session replays the same `source` + `messageId` so the identity dedupes it. If the simulator generates new ids per session, a restart would create new signals and interventions. Open question for the MDSS facilitator. (11) Platform Cache is not encrypted here; the cursor sits in it for up to 24 h readable by any Apex in the namespace (guarded only by a test that fails if another class calls `SesionSimulador.leerCursor`). Accepted risk: a cursor is a session handle for a simulator, not a credential, and the Bearer token never enters Apex.
- **Test criteria**: `TelemetriaIngestaTest` (continues from the saved cursor without `POST /session`; with no cursor it opens a session; one job reads several pages and saves the next cursor; every callout sees the same DML count as before execution; an exhausted budget enqueues the continuation with no delay; `iniciar(..., true)` clears the cursor of that scenario and not another's, and `false` keeps it; a 410 on the saved cursor clears it and opens a new session; without cache it opens a new session and flags it; a mid-run failure writes what was read and retries the failed page; a non-retryable mid-run error does not throw; the cursor does not appear in the summary, the cache JSON, the screen detail or the exception message), `SesionSimuladorTest` (alphanumeric key, stable per parameters; save, read, clear; nothing throws without cache) and `IngestaControllerTest` (restart clears only with permission; the detail shows `yaExistentes`; an old summary is ignored; no cache means no detail). They fail if the saved cursor, the restart, the callout-before-DML order is removed or the cursor leaks.

## D032 — What an "invalid" signal is and what stays as evidence (BR-202, US-202)

- **Status**: Proposed (pending confirmation with the MDSS facilitator)
- **Date**: 2026-10-07
- **Context**: BR-202 asks that an invalid signal not stop the others and that there be evidence of which one failed and why, but the brief doesn't define "invalid". The handler already applies concrete rules that until now weren't written down in a single place.
- **Decision**: a signal is invalid, and stays `Rechazada` with `Motivo__c`, when: (1) the value is missing or not numeric, or `occurredAt` is missing or not ISO 8601; (2) its asset doesn't exist in the catalog; (3) its building isn't the asset's building (D031, BR-201); (4) there's no active threshold for its asset type and measurement; (5) its unit isn't the expected one; (6) some field exceeds the allowed length or `Message_Type` isn't an allowed value; (7) the value falls in an `Invalida` severity threshold (physical range). The other signals in the batch continue. The evidence is the `Log_Senial__c` row with its `source|messageId` identity. A signal without `source` or without `messageId`, or with an identity that's too long, can't have a row (the identity is the key): it's only counted in `senialesSinIdentidad` and `rechazadasSinLog`.
- **Alternative dropped**: create a log row even without an identity (with a made-up identity). It would break the "identity = source + messageId" agreement and allow duplicates.
- **Trade-off**: signals without an identity leave only aggregate evidence (a count), not individual evidence.
- **Risk / dependency**: (1) the facilitator may have another definition of "invalid"; if it changes, the rules and the tests (`SenialSensorHandlerTest`) get adjusted. (2) An empty building in the message isn't validated (the signal is processed), and a `Building_Id__c` longer than 50 characters arrives null from `TelemetriaIngesta` (`soloSiCabe`) and isn't validated either: it's a deliberate leniency so as not to reject signals from valid assets; if the facilitator makes the building mandatory, those signals have to be rejected. (3) Rejection by building is terminal for that identity: it depends on the catalog at processing time and, even if the catalog is fixed later, a resend of the same message counts as a resend and isn't reprocessed, so a critical reading rejected this way doesn't open an intervention (same as with an unknown asset); the action is to fix the catalog and have the source send a new `messageId`. (4) If the `External_Id__c` of the org's accounts doesn't match the `externalId` the simulator sends, every signal with a building would be rejected: confirm with a real run after loading the catalog.
- **Test criteria**: `SenialSensorHandlerTest`: mixed batch of 200 (missing value, missing date, unknown asset, incompatible unit), `unaMedicionConUnidadIncompatible...`, `unEdificioQueNoEsDelActivo...` (another building), `elReenvioIdenticoDeUnEdificioAjeno...` (resend), `elMismoMensajeConElEdificioCorregido...` (conflict), `unEdificioVacioNoSeValida...` (empty-building policy) and long identity / no identity in the `rechazadasSinLog` tests.
- **Note (2026-10-16), scope**: what this entry says about signals without an identity applies to the subscriber. Simulator messages without `source` or `messageId`, or with an identity longer than 60 characters, never reach it: `TelemetriaIngesta` rejects them before publishing and does leave them a `Rechazada` row with a key derived from a hash (`SIN-ID|`, `ID-LARGA|`), as D013 says (point 3). That's exactly the alternative this entry drops for the subscriber. It's still to be decided whether both layers should follow the same rule.
- **Next action**: ask the facilitator about this list; move to Accepted or adjust.

## D034 — The history shows measurement type, value and unit (HP-07)

- **Status**: Proposed
- **Date**: 2026-10-07
- **Context**: D024 (risk 1) and D030 (risk 3) left the history without values because `Log_Senial__c` doesn't store them: only `Message_Type__c` (`MEASUREMENT` or `CONNECTIVITY`). The operator saw "Medición · Conflicto" without knowing which measurement or what value, and couldn't see how it changed over time. The values need to be stored when the signal is processed, and shown.
- **Decision**: (1) Three new fields on `Log_Senial__c`, named after the event's fields: `Measurement_Type__c` (text 60), `Unit__c` (text 40) and `Value__c` (number 18,4). They're free text and number, not restricted picklists: a picklist would reject the upsert of a row with an unknown type or unit, and the evidence of exactly what arrived wrong would be lost. (2) `SenialSensorHandler` writes them on the first processing of an identity, with the value as it arrived and whatever the result (including `Rechazada`, `Atrasada`, `Superada`); for connectivity they stay empty; the type and unit are trimmed to the field length and a value that doesn't fit is stored empty, so these fields never make the log upsert fail. A resend doesn't touch them and a `Conflicto` doesn't overwrite them: the original content is kept. (3) `getHistorial` returns them as `measurementType`, `unit` and `value` in the same `SYSTEM_MODE` read from D024, behind the `USER_MODE` asset check; the rest of the technical data (`Motivo__c`, `Huella__c`, identity) still isn't returned. (4) `novaCasaHistorialSenales` adds the "Medición" and "Valor" columns (with the unit). (5) `Nova_Casa_Admin` (read-only) and `Nova_Casa_Procesamiento` get FLS on the new fields; the operator, coordinator and manager don't need it because the history is read in `SYSTEM_MODE`.
- **Alternative dropped**: reading the value from `Lectura_Vigente__c` (it only stores the latest one per asset and type, not the history); storing the full payload in a long field (exposes technical data and grows without control); restricted picklists as in `Lectura_Vigente__c`.
- **Trade-off**: more columns and a change in `SenialSensorHandler` (Juan Diego's area) in exchange for a history that explains what arrived; rows from before this change stay without a value ("—") and aren't backfilled (the log didn't store the data).
- **Risk / dependency**: (1) It touches `SenialSensorHandler`, `Nova_Casa_Admin` and `Nova_Casa_Procesamiento`: let Juan Diego know before the deploy, and deploy the fields and permissions before the Apex. (2) The fields are data the operator sees in the history: confirm with the facilitator that showing the value of a rejected or conflicting signal is acceptable (BR-209). (3) `Value__c` stores 4 decimals; a value with more is rounded when saved. (4) The LWC has no Jest (D012): the columns are tested by hand. (5) A `Rechazada` row shows a value that looks like a reading: the history note says it wasn't accepted and doesn't change state; the value is shown with up to 4 decimals so it isn't rounded across a threshold. (6) Reviewed on 2026-10-09: the behavior of the three cases this entry left without a test now has tests in `SenialSensorHandlerTest`: the same identity twice in one batch (`laMismaIdentidadDosVecesConContenidoDistintoEnUnLoteEsConflictoYNingunaGana`), `Atrasada` without touching `Lectura_Vigente__c` (`unaSenialMasAntiguaQueLaVigenteQuedaAtrasadaAunqueSeaCritica` and the two about an older critical signal in the same batch, D011 h) and reprocessing a `Fallida` (`elReintentoTrasUnaFallidaConLaMismaHuellaSeProcesaYLaDeOtroContenidoEsConflicto`). What's still unchecked is what's specific to this entry: none of those tests looks at `Measurement_Type__c`, `Unit__c` or `Value__c`, so there's no test that they get written on an `Atrasada`, on a `Superada` or on a `Fallida` reprocess.
- **Test criteria**: `SenialSensorHandlerTest` (the first processing stores type, unit and value, including on `Rechazada`; connectivity leaves them empty; a resend doesn't change them; a conflict doesn't overwrite them; a long type and unit get trimmed and a huge value is left empty without failing the upsert) and `ActivosOperadorControllerTest` (the history returns those three keys and nothing technical; an old row returns them as null; someone else's asset is still denied). They fail if the write or the read is removed.
- **Next action**: dry-run, notice to Juan Diego, PR by John (Juan Diego reviews), deploy the fields and permissions first, run the tests by hand and try a real run to see the values in the history.

## D035 — Bulk close an asset's open interventions (US-205, US-207)

- **Status**: Proposed (pending Juan Diego's review)
- **Date**: 2026-10-07
- **Context**: the baseline agreement is one intervention per unique critical message (D010; the baseline design's limitation is in D033, point 6), so an asset with many different critical messages piles up many open interventions (on 2026-10-07 "Cámara acceso vehicular" had 25 after a scenario run). The operator screen shows the most recent one and "y N más"; closing it brings up the next one, and closing them one by one makes no sense for whoever handles them.
- **Decision**: we add the "Cerrar las N abiertas" action to the asset detail, which calls `IntervencionOperadorController.cerrarIntervencionesDelActivo`. It uses the same custom permission as "Actualizar seguimiento" (`Nova_Casa_Seguir_Intervencion`) and the same user mode (`USER_MODE`): it only closes the `Case` records the persona can see and edit, each one separately. It closes up to 200 per call and warns if more remain. It leaves a "Cierre en bloque" line (with the optional comment) in each Case's `Description`, so who and when is recorded. Creation doesn't change: one intervention per unique critical message.
- **Alternative dropped**: consolidate into a single open intervention per asset at creation time. The baseline agreement says that consolidating different keys into one open incident is extra scope, and it would require deciding it with the facilitator and running the scenarios again.
- **Trade-off**: bulk close loses each Case's individual status (they all move to `Closed`); the detail of what happened with each one is only kept in its `Description`. It can't be reopened from the screen (same as with "Actualizar seguimiento").
- **Risk / dependency**: (1) if a persona can't see some of the asset's Cases, those stay open and the asset can keep showing interventions. (2) If a Case fails to save, the rest still close and the screen reports how many failed. (3) The query takes the oldest first and doesn't remember which ones failed: if 200 or more of the oldest can't be saved, each click retries the same ones and never reaches the rest; the screen says so instead of asking for another click. (4) The number on the button comes from `openInterventionCount`, which is cut off at 2000 rows per screen; that's why with more than 200 the button says "hasta 200". (5) The screen sends the number the persona saw; if it changed (ingestion keeps opening interventions), the server closes nothing and asks to confirm again, so a new critical one is never closed without being seen. If that number is cut off by the screen's 2000 rows, the action is rejected until it goes down. (6) If the `Description` is already full, the close line is kept and the oldest text is lost; the comment is saved on a single line so nobody can fake another person's line (`actualizarSeguimiento` keeps its previous behavior).
- **Test criteria**: `IntervencionOperadorControllerTest`: closes all open ones for the asset and only for that asset (leaves the already closed one and the other asset's one untouched), leaves the line with and without a comment, rejects the operator and the manager for lack of permission (not for visibility), rejects bad input / invisible asset / nothing open, doesn't close a Case it can only read (counts `fallidas`), closes nothing with the custom permission but without Edit on `Case`, doesn't close if the number the persona confirmed changed, leaves a single line even if the comment contains line breaks (and keeps it when the `Description` is full), and with 201 open closes 200, warns that there are more, and the second call closes the last one. `IntervencionServiceTest`: a resend with the same identity, after its Case is closed, returns the same Case and doesn't open another one (bulk close makes that state common).
- **Next action**: dry-run, deploy from `main` after the merge, test in the browser as coordinator with an asset that has several open ones.

## D036 — The follow-up status comes from the `Case.Status` picklist; the Case compact layout shows the origin (HP-07)

- **Status**: Proposed
- **Date**: 2026-10-08
- **Context**: "Actualizar seguimiento" offered En curso / En espera / Cerrada (D020, point 2), a list written twice: `FOLLOW_UP_OPTIONS` in `novaCasaActivosOperador` and `FOLLOW_UP_STATUSES` in `IntervencionOperadorController`. The Spanish labels belonged to the LWC, on top of picklist values: "En espera" on top of `On Hold` and "Cerrada" on top of `Closed`. The `Case` page offers the five values of the `Case.Status` picklist (On Hold, Escalated, Closed, New, En curso, the order of the repo's value set). Two vocabularies for the same field "makes no sense", and nothing forced them to match. Also, the `Case` compact layout showed `Identidad_Senal__c`, which is only filled in on `Case` records opened by a critical signal and is empty by design on manual interventions (Origin `Operador`, D020 point 3): the summary of those Cases looked incomplete.
- **Decision**: (1) The "Estado" dropdown and the server validation read the active values of the `Case.Status` picklist. `IntervencionOperadorController.getEstadosSeguimiento()` (`cacheable`) returns them as `value` + `label`, in picklist order, and `actualizarSeguimiento` checks the received status (API value) against that same set; the two hand-written lists are removed. That way the asset panel and the `Case` page always offer the same options. This replaces the fixed En curso / En espera / Cerrada list in point 2 of D020. `getEstadosSeguimiento` doesn't require a custom permission: it's picklist metadata, not record data, and it changes nothing. The rest of `actualizarSeguimiento` doesn't change: `Nova_Casa_Seguir_Intervencion` is checked first, the query runs in `USER_MODE` and only takes Cases with an asset that aren't closed (a closed `Case` still can't be reopened from the panel), `update as user`, the comment, and the error messages. In the LWC the default status is "En curso" if it's among the options; if not, the first one that isn't `Closed`. If the list doesn't load or comes back empty, the form shows a warning and "Guardar" stays disabled. (2) In the same branch, the `Case` compact layout shows `Origin` instead of `Identidad_Senal__c`, and the `Identidad_Senal__c` field gets help text: it's only filled in on Cases opened by a critical signal and is empty by design on manual interventions. This is a change to `Case` metadata, which is shared metadata; the LWC and the controller don't depend on it.
- **Alternatives dropped**: (a) make `Status` read-only on the `Case` layout: it would force anyone who starts from a `Case` (coordinator) to always go through the asset. (b) Trim the `Case.Status` picklist to 3 values or give it Spanish labels: it removes values from the picklist, is hard to undo and, per `CONTRIBUTING.md`, goes in its own PR, with agreement from both of us, and deploys only from `main`; it stays as an agreed follow-up. (c) Add the 5 values to the LWC by hand: it would duplicate the list again and bring the same problem back.
- **Trade-off**: a single source of truth in exchange for losing control of the vocabulary in the panel: whatever the picklist offers, the panel offers, including values that D020 had left out on purpose.
- **Risk / dependency**: (1) `New` and `Escalated` now show up in the panel. (2) The labels end up mixed, Spanish and English (En curso, On Hold, Closed), until the picklist is renamed; also, two options that already existed switch from Spanish to English for the coordinator: "En espera" is now `On Hold` and "Cerrada" is `Closed`. (3) The `Case` page can still reopen a closed `Case`; the panel can't, and it still rejects closed Cases. (4) If an admin adds an active value to the picklist it shows up in the panel on its own and the server accepts it; if they deactivate it, it disappears and the server rejects it with `INVALID_STATUS`. The four open values (`New`, `En curso`, `On Hold`, `Escalated`) have `closed=false` and the "open intervention" guards (`OpenCaseCheck`, `ActivosOperadorController`) use `IsClosed`; `IntervencionService` deduplication looks up by `Identidad_Senal__c` without looking at `Status`. So moving a Case between those values doesn't change the open count or the one-intervention-per-unique-critical-message rule (BR-205). A new value with `closed=true` would behave like `Closed`: the panel would offer it, but the Case could no longer be reopened from it. (5) The LWC requests the list when the screen loads, for every role; the manager has no access to the class, so for them the call fails silently and it doesn't matter, because they never open the form. (6) The LWC has no Jest (D012): the empty-list or error warning is tested by hand. (7) The compact layout and the field are `Case` metadata, which is shared (`CONTRIBUTING.md`): we have to tell Juan Diego on Slack and confirm he has no open change on `Case` before deploying them.
- **Test criteria**: `IntervencionOperadorControllerTest`: `getEstadosSeguimiento` returns exactly the active values of the `Case.Status` picklist; a value outside the picklist is rejected with `INVALID_STATUS`; a picklist value the previous list didn't have (`Escalated`) is accepted; the server accepts every value the list offers; a closed `Case` is still rejected with `CASE_NOT_FOUND` for each of them; `getEstadosSeguimiento` also responds to someone without the custom permission; the permission checks (operator and manager rejected, coordinator accepted) don't change. They fail if the server goes back to a fixed list or stops validating against the picklist.
- **Next action**: dry-run handled by `sf-deployer`; PR from John (Juan Diego reviews it); deploy only this story's files; ask John and Juan Diego whether we do the separate PR to clean up the picklist (3 values, Spanish labels).

## D037 — The "Lectura vigente por tipo" table in the asset detail adds the "Antigüedad" column (US-207, HP-07)

- **Status**: Proposed (deployed with PR #68)
- **Date**: 2026-10-09
- **Context**: BR-207 asks that the operator "reconoce la antigüedad de la información". D033 (point 2) put each reading's age on the asset card (`novaCasaActivoEstado`), but the `novaCasaActivosOperador` detail only showed it in the headline and in the "última señal" line, not per reading. The prototype `entregables/02-prototipo-baja-fidelidad.html` defines that table with three columns (Medición, Valor, Severidad), so adding a fourth is a departure from the prototype, which guides the design but isn't the spec (`AGENTS.md`).
- **Decision**: (1) The detail's "Lectura vigente por tipo" table gets the "Antigüedad" column with each reading's age (`hace 5 min`), and "—" in the "Sin lecturas" rows. (2) `readingAge()` reuses `relativeAge` from `novaCasaEtiquetas`, with a clock tolerance: a source time up to 5 minutes ahead of "now" (`FUTURE_TOLERANCE_MS`, the same one the "última señal" text uses) reads as recent; beyond that it shows "hora del simulador", never a negative age. (3) The same age text feeds the headline (`headMeasure`) and the last-reading line (`lastSub`), so all three match. (4) Same branch change: `novaCasaEdificioResumen` imported `reduceError` incorrectly and, on a server error, the `Account` summary got stuck loading; it now imports it from `c/novaCasaEtiquetas`. This is a fix, not a design decision.
- **Alternative dropped**: keep the table at the prototype's three columns and the age only in the headline and the last-reading line (with several readings per asset you couldn't tell which one is old).
- **Trade-off**: one more column in a narrow table, in exchange for being able to compare the age of each measurement type, which is the point of having "asset + tipo" as the current reading.
- **Risk / dependency**: (1) Two components currently apply different rules to a slightly future source time: `novaCasaActivoEstado` calls `relativeAge` without tolerance and shows "hora del simulador" for any time ahead of "now"; `novaCasaActivosOperador` reads it as recent up to 5 minutes. A reading 1 minute ahead would look different on the asset card and in the detail; it wasn't unified so as not to touch `novaCasaActivoEstado` in this PR. (2) We set the 5-minute threshold ourselves; it doesn't come from MDSS or from the simulator. It's an LWC presentation constant, not one of the normal, warning and critical thresholds of BR-204 (those live in `Umbral__c`); the same goes for the 60-minute "dato antiguo" cutoff in `novaCasaEtiquetas`. (3) The LWC has no Jest (D012): the column is tested by hand. (4) `novaCasaActivosOperador` belongs to Juan Diego (D033, risk 1).
- **Test criteria**: manual, because there's no Jest (D012): as `novacasa.operador`, open the detail of an asset with readings of two types and check that the "Antigüedad" column shows one age per row and "—" for a type with no reading, that it matches the headline and "última lectura", and that a reading with a future source time shows "hora del simulador" and not a negative age; open an `Account` and check that the building summary loads. No run recorded yet (see `evidencia-escenarios.md`, US-207).
- **Next action**: do the manual check and record it; decide whether `novaCasaActivoEstado` adopts the same 5-minute tolerance (in its own change).
