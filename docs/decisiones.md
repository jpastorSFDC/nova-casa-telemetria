# Decisiones y riesgos (ADR-lite)

Entregable 6 de Discovery. Cada decisión no obvia se registra aquí con su alternativa descartada y el trade-off, para que nadie —humano o IA— la revierta sin darse cuenta de por qué se tomó.

No confundir con la sección "Acuerdos" de `Sprint 2 - Nova Casa.md` (verbatim de MDSS): esos son los acuerdos **ya cerrados** por el brief/facilitador y no se contradicen sin volver a documentarlos y probarlos aquí. Este archivo es donde el par **propone y registra sus propias decisiones** dentro de esos límites.

## Cómo agregar una entrada

Copiar esta plantilla, numerar secuencialmente, y mantener el estado actualizado.

```markdown
## D00X — <título corto>

- **Estado**: Propuesta | Aceptada | Rechazada | Reemplazada por D0YY
- **Fecha**:
- **Contexto**: ¿qué problema o ambigüedad obliga a decidir?
- **Decisión**: qué se hace.
- **Alternativa descartada**: qué otra opción se consideró.
- **Trade-off**: qué se gana y qué se sacrifica con la decisión elegida.
- **Riesgo / dependencia**: qué podría invalidar esto y de qué depende.
- **Siguiente acción**: qué falta para validarlo o implementarlo.
```

## D001 — Objeto de intervención: Case

- **Estado**: Aceptada
- **Fecha**: 2026-09-29
- **Contexto**: BR-205/BR-206 requieren que una señal crítica produzca una intervención operativa que el coordinador de mantenimiento pueda revisar y dar seguimiento. El acuerdo de MDSS ("Incidente") exige el comportamiento (una intervención como máximo por mensaje crítico único) pero no fija el objeto Salesforce que la representa. `CONTRIBUTING.md` ya nombraba `Case` como archivo compartido y hablaba de "cases" creados por la ingesta antes de que esta decisión quedara registrada aquí.
- **Decisión**: la intervención se modela como `Case` (objeto estándar).
- **Alternativa descartada**: `Work Order`.
- **Trade-off**: `Case` viene habilitado en la org sin configuración adicional y reutiliza procesos, permisos, queues y vistas de lista que el equipo ya conoce. Se sacrifican los campos propios de mantenimiento de `Work Order` (Work Type, Service Appointment), que además requieren Field Service — no forman parte del alcance base del sprint y no compensan el costo de habilitar y licenciar Field Service solo para esto.
- **Riesgo / dependencia**: si una fase posterior necesita programar visitas técnicas o asignar recursos de campo, puede que se necesite reabrir esta decisión y evaluar Field Service.
- **Siguiente acción**: ninguna para cerrar la decisión; al implementar BR-205/BR-206 revisar si `Case` necesita campos custom (severidad, activo relacionado, clave del mensaje) y documentarlos en el modelo de datos.

## D003 — Empate de `occurredAt`: gana la mayor severidad, luego `messageId`

- **Estado**: Aceptada
- **Fecha**: 2026-10-01
- **Contexto**: el acuerdo de Discovery deja pendiente la regla para cuando dos señales válidas del mismo `asset`+`measurement.type` llegan con el mismo `occurredAt` — exige que sea determinista y prohíbe que el orden de llegada decida.
- **Decisión**: gana la lectura con mayor severidad resultante (comparando contra `Umbral__c` igual que en clasificación normal, usando el mismo nivel numérico que ya alimenta `Severidad_Nivel__c`). Si la severidad también empata, se usa `messageId` como segundo criterio, en orden alfabético ascendente (puramente determinista, sin significado de negocio).
- **Alternativa descartada**: desempatar solo por `messageId` sin pasar primero por severidad — más simple de implementar, pero puede dejar como vigente una lectura menos severa cuando ambas comparten timestamp, lo que iría contra el espíritu de "ver la condición más crítica sin ambigüedad" del problema de Laura. También se descartó marcar el caso como `Conflicto` sin elegir ganadora: el acuerdo pide explícitamente una regla que sí decida, no que aplace la decisión a revisión humana.
- **Trade-off**: la regla de severidad es más fiel al objetivo del producto, a cambio de depender de que la clasificación de severidad ya esté resuelta en el mismo paso de procesamiento (no es un criterio independiente y aislado como lo sería `messageId` solo).
- **Riesgo / dependencia**: depende de que los umbrales (`Umbral__c`, ver pendiente abajo) tengan valores reales antes de poder implementar y probar esta regla con casos concretos.
- **Siguiente acción**: implementar en la lógica de clasificación (Apex, aún sin empezar) y cubrir con un test que falle si el empate se resuelve por orden de llegada en lugar de severidad.

## D004 — `Umbral__c` es objeto custom, no Custom Metadata Type

- **Estado**: Aceptada
- **Fecha**: 2026-10-01
- **Contexto**: BR-204 pide que los límites de clasificación sean administrables sin redesplegar código. Custom Metadata Type (`__mdt`) es la opción por defecto para ese tipo de dato de configuración, pero sus registros solo se editan desde Setup y requieren el permiso de sistema "Customize Application" — exclusivo de administrador. El acuerdo del sprint es que un perfil no-admin (operador/coordinador) pueda ajustar los umbrales sin que se le dé acceso de administrador.
- **Decisión**: `Umbral__c` se modela como objeto custom estándar (`__c`), no como Custom Metadata Type. El acceso de edición se controla con FLS/permission set sobre el objeto, igual que cualquier otro dato operativo.
- **Alternativa descartada**: `Umbral__mdt` (Custom Metadata Type).
- **Trade-off**: se gana poder darle edición a un perfil no-admin sin tocar "Customize Application"; se sacrifica lo que CMDT da gratis (los registros viajan como metadata y se despliegan solos entre entornos, sin Data Loader ni scripts de datos).
- **Riesgo / dependencia**: ninguno funcional. Falta que el permission set que dé acceso a `Umbral__c` quede definido (ver D005/BR-208) para que la edición no-admin sea real y no solo teórica.
- **Siguiente acción**: al definir el permission set del operador/coordinador (D005), incluir CRUD/FLS de `Umbral__c` para el perfil que deba poder ajustar los límites.

## D006 — Siembra de `Umbral__c` desde la carga del catálogo (HP-04)

- **Estado**: Propuesta
- **Fecha**: 2026-10-05
- **Contexto**: T3.2 pide un umbral por cada combinación del catálogo. `Umbral__c` no tiene campo de id externo y `/catalog` entrega `thresholdsReference` como rangos (min/max), no como operador + valor.
- **Decisión**: `CatalogoService.loadCatalog()` siembra `Umbral__c` con la tabla de referencia del equipo (T2.7), una vez por cada `asset.type` + `measurement` del catálogo (la unidad sale del catálogo). Si esa combinación ya tiene cualquier `Umbral__c` (editado, desactivado o no), no se siembra nada para ella.
- **Alternativa descartada**: clave natural completa (tipo, medición, severidad, operador, valor, unidad): un umbral editado dejaría de coincidir y se duplicaría. Un campo de id externo: cambio de modelo sin necesidad.
- **Trade-off**: se gana idempotencia y respeto a lo que el usuario cambió; se sacrifica que un umbral borrado a mano no se restituye solo, ni se agregan reglas nuevas a una combinación ya sembrada.
- **Riesgo / dependencia**: operadores y valores siguen "por acordar" (ver pendiente 1 abajo); la tabla vive en el código como valor inicial, la fuente operativa es el objeto.
- **Criterios de prueba**: `CatalogoServiceTest` demuestra la regla: un umbral por combinación (`shouldSeedOneThresholdSetPerCombination_WhenCatalogIsValid`), recargar no duplica (`shouldNotDuplicateThresholds_WhenLoadedTwice`), un umbral editado o desactivado se conserva (`shouldKeepEditedThreshold_WhenCatalogIsReloaded`), un conjunto parcial no se completa (`shouldNotCompletePartialSet_WhenCatalogIsReloaded`) y un usuario sin acceso a `Umbral__c` recibe una `CatalogoServiceException` envuelta (`shouldThrowException_WhenRunningAsUserWithoutUmbralAccess`).
- **Nota**: sembrar estos operadores y valores significa que el equipo ya los escogió en la práctica; siguen pendientes de confirmación del facilitador.
- **Siguiente acción**: confirmar operadores y valores con el facilitador.
## D007 — La antigüedad de la señal se marca con un parámetro de presentación (`staleMinutes`), no con un umbral

- **Estado**: Propuesta
- **Fecha**: 2026-10-05
- **Contexto**: BR-207 pide que el operador reconozca la antigüedad de la información. La pantalla necesita un corte para marcar una señal como "desactualizada". El acuerdo "Umbrales fuera del código" cubre los límites de clasificación de severidad (D004), no este corte.
- **Decisión**: el corte es una propiedad de diseño del LWC (`staleMinutes`, 15 por defecto), editable en Lightning App Builder para páginas App y Home. Solo decide si se muestra la marca "(desactualizada)"; no influye en la severidad ni en ninguna decisión del servidor. El valor por defecto vive en una sola constante del JS, con el mismo valor en `js-meta.xml`.
- **Alternativa descartada**: valor por tipo de activo o de medición en `Umbral__c` o Custom Metadata. Agrega un objeto o un despliegue y no hay una cadencia de emisión por sensor acordada que lo justifique.
- **Trade-off**: se gana una pantalla simple y ajustable sin tocar código ni datos; se sacrifica un corte distinto por tipo de sensor, de modo que un sensor lento puede verse "desactualizado" sin estarlo. Con la ubicación Tab no hay configuración y rige el valor por defecto.
- **Riesgo / dependencia**: si la cadencia real del simulador supera los 15 minutos, habrá falsos "desactualizada". Hay que contrastar el valor con la cadencia de emisión del simulador.
- **Siguiente acción**: validar los 15 minutos contra el simulador. Criterio de prueba: una señal por debajo del corte no lleva marca, una por encima la lleva, y la ubicación Tab usa el valor por defecto.

## D009 — La pantalla del operador asume lecturas válidas en `Lectura_Vigente__c` y desempata por Id

- **Estado**: Propuesta
- **Fecha**: 2026-10-05
- **Contexto**: el acuerdo dice que la severidad del activo es la más alta de sus últimas lecturas válidas. `Lectura_Vigente__c` no tiene un campo de validez. Además, D003 desempata por mayor severidad y luego por `messageId`, dato que este objeto no guarda.

## D013 — Ingesta en cadena de Queueable, log 'Publicada' antes del evento, y qué pasa con lo que no cabe o no se publica

- **Estado**: Propuesta
- **Fecha**: 2026-10-05
- **Contexto**: US-201 necesita traer `/telemetry` página a página (cursor del simulador), dejar constancia de "publicada" separada de "procesada" y publicar `Senial_Sensor__e`. El contrato de MDSS no cubre la apertura de sesión ni el header `X-Simulator-Cursor` (ver `docs/entendimiento.md`), ni qué hacer si un evento no se puede publicar o un valor no cabe en el campo.
- **Decisión**:
  1. `TelemetriaIngesta` es una cadena de Queueable, un trabajo por página: callouts primero (`POST /session` solo en el primer trabajo, luego `GET /telemetry`), después DML (insert de `Log_Senial__c` como `Publicada`, `EventBus.publish`, update), y al final el encolado del siguiente. Nunca hay un callout tras un DML en la misma transacción. Se corta con `hasMore=false`, página vacía, tope de páginas (25 por defecto, máximo 100) o profundidad de cola agotada.
  1.bis. **Corrección 2026-10-05**: en una corrida real (`DUPLICATES`) la cadena no se cortó con el `WARN` esperado: `AsyncInfo.hasMaxStackDepth()` devolvió `false` un trabajo tarde y el sexto trabajo (profundidad 5) quedó `Failed` con `Maximum stack depth has been reached` (excepción no capturada), perdiendo el resto de la ingesta. Arreglo en `TelemetriaIngesta`: (a) el encolado del siguiente trabajo pide al plataforma una profundidad mayor con `System.enqueueJob(siguiente, opciones)` y `AsyncOptions.MaximumQueueableStackDepth = 30` (`PROFUNDIDAD_COLA_SOLICITADA`); (b) un respaldo propio, independiente de lo que reporte la plataforma, corta la cadena en `pagina >= 27` (`PROFUNDIDAD_LOCAL_MAXIMA`) con el mismo `WARN` de siempre, nunca con un fallo sin capturar. 27 queda por encima del tope por defecto (25) a propósito: una corrida sin `maxPaginas` explícito no debe cortarse por este respaldo. No está validado empíricamente que la plataforma honre una profundidad de 30 en `nova-cdo` (es una organización trial/developer); si una corrida futura pide más de 27 páginas y la plataforma de verdad tiene un techo menor a 30, el mismo fallo podría repetirse y los dos números habría que subirlos o cambiar de mecanismo (por ejemplo, reanudar con Scheduled Apex, que abre un contexto async nuevo). Pendiente de confirmar con una corrida real que pida más de 27 páginas.
  2. El cursor viaja solo como estado privado del siguiente trabajo: no se escribe en registros, logs, mensajes de excepción ni fixtures. Los mensajes de excepción del cliente llevan solo la operación, el código HTTP o el nombre del tipo de excepción, nunca el cuerpo ni el mensaje original (un `JSONException` o un `CalloutException` pueden citar el cuerpo o la petición).
  3. Nada se descarta en silencio (BR-202, BR-209). Cada descarte deja una fila `Log_Senial__c` con `Resultado__c = 'Rechazada'` y `Motivo__c`: mensajes sin `source` o `messageId`, con `source` o `messageId` de más de 80 caracteres o con identidad `source|messageId` de más de 60, y elementos de `data` que no son objetos (posición y página en el motivo). Como la identidad real no cabe o no existe, la clave de la fila es un hash (`ID-LARGA|...`, `SIN-ID|...`, `DESCARTE|...`): el mismo mensaje repetido cae en la misma fila. Estos mensajes no se publican. `Source__c` y `Message_Id__c` se guardan truncados al largo del campo; nunca se guarda el contenido de un elemento que no es objeto.
  4. Si el insert de la fila de log falla por algo distinto de duplicado, el evento no se publica (un evento sin fila sería intrazable) y queda en los contadores `logsFallidos` y `noPublicadosPorLog` y en una línea `WARN` del trabajo (solo números). No hay fila que lo pruebe, porque el insert falló; esa es la constancia mínima y queda abierta (ver más abajo).
  5. Si `EventBus.publish` falla para un evento, la fila que esta corrida creó pasa a `Fallida` con el código de estado en `Motivo__c`. Un reenvío (identidad ya existente) no toca la fila y se publica igual, para que el suscriptor lo cuente. Lo mismo vale para una fila `Fallida`, y para el mismo mensaje con contenido distinto: la ingesta no compara contenido, el conflicto (misma identidad, otra huella) lo decide el handler. `Huella__c` la escribe el handler.
  6. Dos eventos con la misma identidad en la misma página: el primero crea la fila, el segundo recibe `DUPLICATE_VALUE` dentro del mismo insert y cuenta como `yaExistentes`. Los dos se publican.
  7. Todo el DML corre `without sharing` y en `SYSTEM_MODE` (la ingesta no depende de permisos de operador), pero el callout no es independiente: el usuario que llama `iniciar()` (el trabajo corre como él) necesita el permission set `Nova_Casa_Simulator_Integration`, que da acceso al principal `NovaCasaSimulatorPrincipal` del Named Credential. Además necesita permiso de crear sobre `Senial_Sensor__e` para publicar; ese permission set hoy no lo concede (ver más abajo).
  8. Tras un fallo a mitad de cadena el trabajo que falló queda visible en Apex Jobs, las páginas anteriores ya están en el log y publicadas, y la cadena no sigue. No se guarda el cursor para retomar (sería un secreto en datos). Se vuelve a correr `iniciar()`: abre una sesión nueva, lee desde el principio del escenario y la deduplicación por identidad hace que lo ya ingerido no se duplique ni abra otra intervención; los reenvíos se publican otra vez y el handler los cuenta como reenvíos.
  9. Mayúsculas y minúsculas: `Identidad__c` está marcado único (`unique=true`) sin `caseSensitive` explícito en el metadata del repo, así que el comportamiento depende del valor por defecto de la plataforma y no se ha comprobado contra el org. El handler compara con una llave en minúsculas (`idKey`). La ingesta usa la identidad tal cual llega. Si el campo distingue mayúsculas, dos mensajes que solo difieren en mayúsculas tendrían dos filas de log pero el handler los trata como una identidad; si no distingue, el segundo cae como duplicado. No se cambió el metadata del campo; queda por confirmar y, si hace falta, cambiarlo en su propia historia.
- **Alternativa descartada**: un solo Queueable que recorre todas las páginas con un bucle: viola el orden callout-antes-de-DML y el tope de callouts por transacción. También se descartó guardar el cursor en un objeto o Custom Setting (secreto en datos) y truncar `source`/`messageId` largos (fusionaría mensajes distintos).
- **Trade-off**: cada página es su propia transacción, así que una falla a mitad deja las páginas anteriores ya publicadas. Reintentar desde el inicio cuesta releer páginas ya ingeridas, a cambio de no guardar el cursor. Un insert de log fallido no deja fila, solo contadores.
- **Riesgo / dependencia**: la forma de `POST /session` (cuerpo `{"scenario": ...}` y respuesta `{"cursor": ...}`) sale de `docs/entendimiento.md` y de la forma de `catalog.json`; no está confirmada contra el simulador real. En orgs developer/trial la cadena se corta a profundidad 5 por defecto; con la corrección de 1.bis se pide una profundidad mayor (30) y se respalda con un tope propio (27), pero el techo real de `nova-cdo` para ese pedido no está confirmado todavía. `Nova_Casa_Simulator_Integration` solo concede el principal del credential, no `Create` sobre `Senial_Sensor__e`: si quien ejecuta `iniciar()` no lo tiene por otro permission set, `EventBus.publish` podría fallar y las filas quedarían `Fallida`; qué hace la plataforma con ese usuario no está comprobado. Los permission sets son metadata compartida: se pide a `sf-metadata-dev`, no se toca aquí.

## D010 — Una intervención (`Case`) por mensaje crítico único, idempotente por identidad y en modo sistema

- **Estado**: Propuesta
- **Fecha**: 2026-10-05
- **Contexto**: BR-205 y el acuerdo "Incidente" piden como máximo una intervención por mensaje crítico único; D001 fijó `Case` como objeto. `Case.Identidad_Senal__c` (único, id externo, 60 caracteres) ya existe para impedir dos Cases del mismo mensaje. Hay que decidir cómo se abre el Case en un lote de hasta 200 y con qué permisos.
- **Decisión**: (1) `IntervencionService.abrir` abre un `Case` por identidad (`source` + `|` + `messageId`), sin consolidar identidades distintas en un incidente abierto. (2) Idempotencia por identidad: una consulta busca los Cases existentes por `Identidad_Senal__c`; si existe, la identidad apunta a ese Case y no se crea ni se actualiza nada; una identidad repetida dentro del lote crea un solo Case. (3) Corre `without sharing` y con `SYSTEM_MODE` (consulta y DML) porque la ingesta se ejecuta como Automated Process y no depende de permisos de operador/admin; la autorización de consulta (BR-208) es otra ruta. (4) Éxito parcial: un solo `Database.insert(..., false)`; cada fallo se devuelve por identidad en `errorPorIdentidad` sin revertir las demás filas. Si el fallo es `DUPLICATE_VALUE` (otra ejecución ganó la carrera), se resuelve al Case ganador con una consulta extra. Los Cases nuevos llevan `Origin` = `Telemetria`, `Status` = `En curso`, `Priority` = `Critica`.
- **Alternativa descartada**: consolidar varias identidades en un incidente abierto por activo (alcance extra sin decisión); `allOrNone` (una fila mala tumbaría el lote de 200); `with sharing` (la ingesta dependería de permisos de usuario).
- **Trade-off**: se gana idempotencia garantizada por la restricción única y aislamiento de errores por fila; se sacrifica una intervención por activo (varias señales críticas distintas abren varios Cases) y que el modo sistema omite FLS/CRUD en esta ruta.
- **Riesgo / dependencia**: el llamador decide qué señal es crítica y no tardía; este servicio no lo valida. Los valores `Telemetria`, `En curso` y `Critica` viven en los standard value sets versionados del repo y deben estar desplegados. La detección de conflicto de contenido (misma identidad, distinto `Huella__c`) pertenece al handler, que no debe llamar a `abrir` para un Conflicto, una señal tardía (Atrasada), un perdedor de desempate (D003) o una señal Rechazada: `abrir` solo recibe señales críticas que ganaron. `abrir` nunca compara contenido y devuelve el Case existente para una identidad conocida. Riesgos: la carrera concurrente `DUPLICATE_VALUE` está resuelta en código pero no tiene prueba.
- **Siguiente acción**: criterios de prueba: reenviar la misma identidad no crea un segundo Case y devuelve el existente; identidad duplicada en el lote crea uno; una solicitud sin identidad o sin `assetId` cae en `errorPorIdentidad` sin afectar a las demás; 200 solicitudes no consumen SOQL/DML por fila.

## D011 — El handler persiste log y lectura vigente, y es dueño de la detección de reenvío, conflicto y señal atrasada

- **Estado**: Propuesta
- **Fecha**: 2026-10-05
- **Contexto**: hasta ahora `SenialSensorHandler` solo clasificaba en memoria. US-201/202/205/206 exigen registrar cada mensaje (publicar no es procesar), mantener la última lectura por activo + medición y abrir una intervención por mensaje crítico único (D010), sin dejar que el orden de llegada decida.
- **Decisión**: (1) Orden de persistencia por lote: consultas (logs por `Identidad__c`, activos por `External_Id__c`, lecturas por `Clave__c`), decisión en memoria, una sola llamada a `IntervencionService.abrir`, upsert de `Lectura_Vigente__c` por `Clave__c`, upsert final de `Log_Senial__c` por `Identidad__c`; todo en `SYSTEM_MODE` con éxito parcial. (2) Una fila en `Publicada` o `Fallida` (o ausente) es primer procesamiento. Una identidad ya procesada con la misma `Huella__c` es reenvío: solo sube `Reenvios__c` y se fija `Ultimo_Reenvio__c`; sin cambio de estado ni intervención. Con distinta huella es `Conflicto`: se marca el log, sin cambio de estado ni intervención. La huella es SHA-256 del contenido sin `deliveryId` ni `publishedAt`. Dentro de un lote, el primer evento de una identidad fija la huella original. (3) Atrasada: una lectura válida estrictamente más antigua (`occurredAt` menor) que la vigente guardada, o que la ganadora del mismo lote para la misma clave, queda en el log como evidencia; `Superada`: la que tiene el mismo `occurredAt` y pierde el desempate D003 contra la vigente o contra la ganadora del lote. Ninguna de las dos sobrescribe la lectura ni abre intervención. Rechazada: dato inválido, sin umbral, unidad incompatible, fuera de rango físico o activo fuera del catálogo. (4) Fallida (T5.16): si no se puede abrir el Case de una crítica ganadora, su log queda `Fallida`, su lectura no se escribe (la vigente anterior sigue intacta) y las demás identidades del lote no se afectan; no hay rollback: si el Case ya se creó (p. ej. falló después el upsert de la lectura), el Case **no se borra** y queda abierto; el reintento con el mismo contenido lo reutiliza porque `abrir` devuelve el Case existente por `Identidad_Senal__c`. Lo mismo si falla el upsert de su lectura. (5) La detección de conflicto de contenido es del handler; `IntervencionService` no compara contenido y solo recibe críticas ganadoras. (6) Endurecimiento: una identidad en `Conflicto` no gana ni abre Case, también dentro del mismo lote (el original y el duplicado distinto quedan fuera de la competencia), y ninguna marca posterior (`Fallida`, `Atrasada`, `Superada`, `Rechazada`) pisa un `Conflicto`. Un reenvío con otra huella sobre una fila `Fallida` o `Publicada` con huella guardada es `Conflicto`, no reemplazo silencioso. `Atrasada` queda solo para lo más antiguo que la lectura (o que la ganadora del lote); perder el desempate D003 con el mismo `occurredAt` es `Superada` (valor nuevo en `Resultado__c`, debe desplegarse antes que el handler). El desempate compara `occurredAt`, severidad, `messageId` y, si aún empatan, el `source`. Las identidades, activos y claves se comparan normalizados (mayúsculas/minúsculas, espacios); `Clave__c` usa el `External_Id__c` del catálogo. Un evento cuyos campos no caben en el destino (identidad/clave 60, `Message_Id__c`/`Source__c` 80, `Delivery_Id__c` 40, `Sensor_Id__c` 50) se rechaza con motivo; si la identidad excede 60 no hay fila de log posible y solo queda evidencia en memoria. El trabajo por evento y cada DML están protegidos con try/catch para que un evento malo no descarte los 200 del lote; un fallo del upsert del log deja contador y detalle (`fallosDeLog`, `erroresDeLog`). El texto no confiable que entra a `Motivo__c` se limpia (sin caracteres de control, máx. 255). La clase es `without sharing` (BR-208: la ingesta no depende de permisos de operador).
- **Alternativa descartada**: escribir la lectura primero y revertirla si falla el Case (un `Savepoint` revertiría también las demás identidades del lote); dejar que `IntervencionService` detecte el conflicto (no conoce la huella ni el estado anterior).
- **Trade-off**: se garantiza que no hay lectura crítica sin intervención y se mantiene el éxito parcial; se sacrifica que, si la crítica ganadora falla, las señales del mismo lote que ella superó quedan `Atrasada` (o `Superada` si empataban en `occurredAt`) y no se promueve la siguiente mejor; una fila `Fallida` que recibe un reenvío con otro contenido pasa a `Conflicto` y ya no se reintenta por reenvío igual; y el reenvío no refresca `Procesado_At__c`.
- **Riesgo / dependencia**: el log solo puede dar fe de un reenvío si la fila ya existe (la ingesta la inserta en `Publicada`); el orden dentro del lote decide cuál evento es el original si una misma identidad llega dos veces con contenido distinto en el mismo lote. Una fila ya `Procesada` que recibe un conflicto pasa a `Conflicto` y conserva `Caso__c`. Implementado con pruebas en `SenialSensorHandlerTest`; desplegado en `nova-cdo` (deploy 0Afak00000nMLSzCAO) y probado con `sf apex run test`: 34 de 34, cobertura 97 % del handler y 100 % del trigger.
- **Límites conocidos (aceptados)**: (a) un evento sin `source` o `messageId`, o con identidad de más de 60 caracteres, no deja evidencia persistente: solo contadores y mapas de la transacción (`senialesSinIdentidad`, `rechazadasSinLog`). (b) `Duplicada` sigue en la picklist `Resultado__c` pero el handler nunca la escribe (reservada): el reenvío se registra con `Reenvios__c` y `Ultimo_Reenvio__c`, sin cambiar `Resultado__c`. (c) Se aparta de los valores de `Resultado__c` del prototipo `entregables/03-arquitectura-flujo-datos.html` (Procesada · Duplicada · Atrasada · Invalida · Publicacion rechazada): el handler usa Publicada, Procesada, Rechazada, Atrasada, Superada, Conflicto y Fallida; el prototipo guía el diseño pero no es la especificación. (d) Si el `source` contiene `|`, `desdeVigente` parte mal la identidad guardada (`source|messageId`) y el desempate D003 contra la lectura vigente puede comparar un `messageId` incorrecto; el simulador no usa `|` en `source`. (e) `Lectura_Vigente__c.Unidad__c` y `Log_Senial__c.Message_Type__c` son picklists restringidas sin longitud propia. `Message_Type__c` se valida contra los valores de la picklist (`Schema` describe, sin SOQL/DML): un valor no vacío fuera de ella queda `Rechazada` con motivo que nombra el campo, no se copia a la fila de log, no escribe lectura ni abre Case; un valor vacío se comporta como antes. Para `Unit__c` el handler solo rechaza más de 255 caracteres: un valor corto fuera de la picklist no se valida y haría fallar el upsert de esa fila (queda en `fallosDeLog`). (f) `Occurred_At__c` de Salesforce no guarda milisegundos: el handler trunca `occurredAt` a segundos al leer el evento, de modo que la comparación con la lectura vigente guardada usa la misma precisión y el empate D003 no lo decide el orden de llegada; dos señales que solo difieren en milisegundos cuentan como el mismo `occurredAt`. (g) Si falla el procesamiento de un evento en la etapa de decisión, su fila `Fallida` lleva `Source__c`, `Message_Id__c`, `Occurred_At__c` y `Procesado_At__c` (los dos primeros son obligatorios); no se escribe `Huella__c`, así que no se pisa la original. (h) Una señal con `occurredAt` menor que la ganadora del mismo lote, para el mismo activo y tipo de medición, queda `Atrasada` (motivo "Más antigua que ... (el lote)"), igual que una más vieja que la lectura vigente: se conserva como evidencia, no sobrescribe la lectura y no abre Case aunque sea crítica. Decidido por John el 2026-10-05 tras la corrida `QA_200` (167 de 189 filas quedaron así). Se descartó marcarlas `Superada`, que queda reservada para el empate D003.
- **Siguiente acción**: criterios de prueba: reenvío igual no cambia lectura ni Case y suma `Reenvios__c`; misma identidad con otro valor queda `Conflicto` sin cambios; señal más antigua queda `Atrasada` sin tocar la lectura ni abrir Case; empate de `occurredAt` lo decide D003 sin importar el orden y el perdedor queda `Superada` (no `Atrasada`); un Case que falla deja `Fallida` y sin lectura mientras otra identidad del lote sí se procesa; 200 eventos usan un número fijo de SOQL/DML.

## D014 — La regla de reintento seguro es una fórmula en `Log_Senial__c` (US-209, T6.1)

- **Estado**: Aceptada
- **Fecha**: 2026-10-05
- **Contexto**: BR-209 pide que el Admin vea el motivo de rechazo y el estado de procesamiento, y que pueda reintentar sin riesgo. - **Decisión**: campo fórmula de texto `Accion_Reintento__c` ("Acción de reintento") en `Log_Senial__c`, calculado con `Resultado__c` y `Reenvios__c`, sin Apex y sin tocar el handler ni la ingesta.   | `Resultado__c` | `Accion_Reintento__c` | Por qué |
  |---|---|---|
  | Fallida | Sí: reintentar; la identidad evita duplicar el caso | El handler la reprocesa como primera vez. `IntervencionService.abrir` devuelve el Case que ya exista por `Identidad_Senal__c` (D010) y la lectura se upserta por `Clave__c`. |

Reintentarla igual es inofensivo: si ya se procesó, el evento nuevo solo suma `Reenvios__c`. (2) Las filas `Rechazada` que deja la ingesta (sin identidad o con identidad larga; claves `SIN-ID|`, `ID-LARGA|`, `DESCARTE|`) nunca se publican: solo se corrigen en origen. (3) Una `Fallida` que vuelve con otra huella pasa a `Conflicto` (D011). (4) `Reintento_Seguro__c` todavía está en el layout de `Log_Senial__c` y en los permission sets `Nova_Casa_Admin` y `Nova_Casa_Procesamiento`.
- **Siguiente acción**: decidir con John si se borra `Reintento_Seguro__c` (y se quita del layout y de los permission sets) en su propio PR desde `main`, y agregar la pestaña de `Log_Senial__c` a la app Nova Casa (metadata compartida, coordinar con John). Criterio de prueba: la consulta agrupada por `Resultado__c` y `Accion_Reintento__c` da un solo texto por estado (dos para los estados finales, según `Reenvios__c`) y ninguna fila "Revisar".

## D018 — Validación al guardar de rangos contradictorios en `Umbral__c` (US-204, T5.10)

- **Estado**: Propuesta
- **Fecha**: 2026-10-05
- **Contexto**: varias filas de `Umbral__c` comparten Tipo_Activo + Tipo_Medicion con distinta severidad y el clasificador aplica la mayor severidad que se cumple. Como la edición de umbrales está abierta a un perfil no admin (D004), un rango mal cargado (p. ej. Advertencia GT 40 y Crítica GT 35) deja la banda de Advertencia inalcanzable sin que nada lo avise.
- **Decisión**: `UmbralTrigger` (before insert y before update) delega en `UmbralValidador`, que rechaza el guardado con `addError` cuando, entre filas activas con el mismo Tipo_Activo + Tipo_Medicion + Unidad_Esperada, una Advertencia queda inalcanzable porque la Crítica cubre todo lo que ella cubre. En dirección superior (GT/GE) el límite crítico debe ser mayor o igual que el de advertencia; en la inferior (LT/LE), menor o igual. Con límites iguales se rechaza si la Crítica es del mismo operador o es GE/LE (Advertencia GE 40 con Crítica GT 40 sí se permite, porque la advertencia sigue disparando en 40). Los pares de distinta dirección y la severidad Inválida no se comparan. También se detectan contradicciones dentro del mismo lote. Una consulta por lote, sin DML, `with sharing`.
- **Alternativa descartada**: validar en el clasificador al ingerir (descartaría señales o las degradaría en silencio, tarde y lejos de quien se equivocó) o una regla de validación declarativa (no puede comparar contra otras filas).
- **Trade-off**: el error aparece al guardar y nombra las dos filas; se pierde flexibilidad: cambiar dos límites fila por fila puede fallar en el paso intermedio (se evita desactivando una fila o guardando ambas en el mismo lote). Con límites iguales la regla es más estricta que un simple "mayor o igual". Cada fila recibe un solo error, el del primer contrario del grupo: armar un mensaje por cada par agotaba el CPU con 200 filas contradictorias (unas 20.000 llamadas); quien edite una fila con varios conflictos ve uno y, al corregirlo, el siguiente.
- **Riesgo / dependencia**: filas ya contradictorias fallarán en su próximo guardado (las 21 activas del org, consultadas el 2026-10-05, cumplen la regla). Límites aceptados: (1) no valida rangos de dirección opuesta que se solapan; (2) no compara la Inválida: como el clasificador la evalúa primero, una Inválida mal cargada (p. ej. GT 10) rechazaría señales válidas, pero con un motivo explicable en el log (`Rechazada`), no como Normal; (3) solo valida filas activas del mismo Tipo_Activo + Tipo_Medicion + Unidad_Esperada; (4) la consulta del validador no aplica FLS a propósito, porque necesita Severidad, Operador y Valor aunque el usuario no tenga FLS sobre ellos; el mensaje de error nombra las otras filas (nombre, severidad, operador y valor), así que un editor sin FLS puede leer esos datos por el error. Las fronteras de D019 son provisionales hasta que el facilitador confirme operadores y valores (D006).
- **Criterios de prueba**: `UmbralValidadorTest` falla si (a) se acepta Advertencia GT 40 con Crítica GT 35 o su equivalente LT/LE; (b) se rechaza el conjunto de referencia sembrado por `CatalogoService`; (c) se acepta el empate GT/GT o GT/GE y se rechaza GE/GT; (d) se compara una fila inactiva, de otra unidad o Inválida; (e) una contradicción dentro del mismo lote no marca ambas filas; (f) 200 filas en un DML usan más de una consulta; (g) una fila con varios contrarios recibe más de un error, o 200 filas contradictorias entre sí exceden el límite de CPU.
- **Siguiente acción**: dry-run, deploy con `RunSpecifiedTests` y `sf apex run test`.

## D025 — The ingestion continues the simulator session across runs (Platform Cache) and one job reads several pages (HP-05)

- **Estado**: Propuesta
- **Fecha**: 2026-10-06
- **Contexto**: verified in `nova-cdo` on 2026-10-06: "Traer señales" always ended with "Terminada · 0 señales registradas". Two causes. (1) `TelemetriaIngesta` chained one Queueable per page and this org stops the chain after 2 jobs (`Ingesta detenida: profundidad maxima de cola alcanzada, paginas=2, recibidos=400, logsCreados=0, yaExistentes=400`), so a run never read more than 400 messages. (2) Every run opened a NEW session (`POST /session`) and the simulator restarts at `msg_000001`, so pages 1 and 2 were always the same 400 messages already stored: all duplicates, no new log row (D013 point 8 had accepted this as a cost). The simulator stream has at least 1600 messages. Read-only probe: simulator cursors are reusable and idempotent (re-reading a cursor gives the same page; an older cursor stays valid after advancing; the `nextCursor` of page 2 continues at `msg_000401..600`); `pollAfterMs` is 10000 but nothing enforced waiting. The MDSS UI keeps ONE session, continues from the saved cursor and only restarts on "Reiniciar sesión".
- **Decisión**: (1) The cursor of the next page is kept OUTSIDE any record, in Platform Cache (org partition `NovaCasaSimulador`, class `SesionSimulador`), with a 24 h TTL and a key that is an alphanumeric hash of scenario + seed + batch size (different parameters never share a stream). It is written after the DML of the pages it follows, and ONLY when every message of the run left a complete trace: if any log insert, publish or failed-mark update failed (`logsFallidos`, `noPublicadosPorLog` or `fallosPublicacion` > 0) the previous cursor is kept (`cursorSinAvanzar`), the run stops without a continuation or retry, and the next run re-reads those pages (idempotent by `source` + `messageId`); the same happens if a job fails. When the stream ends (`hasMore=false`) the cursor of the last page read is kept, so the next run polls it again. The cursor is never logged, returned to the client or put in an exception message. (2) One job reads all requested pages in a loop: first ALL the callouts (each page is turned into rows and events in memory at once to release the heap), then ALL the DML (per page: log insert, publish in chunks of 200, update). Reading stops at the page cap, at `hasMore=false`, on an empty page, at 4000 messages per job (log rows + events stay under 10,000 DML rows; a page that could exceed the budget is not started, and count and time are re-checked after every page), at 45 s of reading (wall clock; the platform allows 120 s of callout time and one request may last 60 s) or when heap (50 %), CPU (60 %) or callouts get close to their limit. A job that stops on budget enqueues a continuation (25 pages are 2 jobs, within what this org allows); if the chain is cut, the saved cursor lets the next run continue. The chain remains only for continuation and retries. (3) Retries on 429/5xx and the 409/410 reopen are kept: a failure after some pages were read writes what was read first and retries the page that failed (a non-retryable error at that point does not throw, because that would roll the DML back: it stops the run and leaves `interrumpidaPorEstado` in the summary); 409/410 clears the saved cursor, opens a new session once per page and re-reads, counted in `sesionesReabiertas`. (4) "Reiniciar sesión": `IngestaController.traerSenales(escenario, paginas, reiniciar)` and a checkbox on the screen; `reiniciar` clears the saved cursor AFTER the job is successfully enqueued (so a failed enqueue leaves the session intact; after the `Nova_Casa_Traer_Senales` custom permission check); the 25-page maximum does not change. (5) Without cache (missing partition, no capacity, platform error) the run opens a new session and says so (`cacheNoDisponible` in the summary and on the screen). (6) `estadoIngesta` returns a `detalle` with the counters of the last run (pages, received, `yaExistentes`, session continued / restarted / no cache, end of stream, status that interrupted it), also kept in the cache and never containing the cursor, so "0 señales registradas" is explained by "N ya existían y se omitieron". A summary older than the start of the run being watched is ignored. (7) `pollAfterMs` is no longer honored with minute delays between pages: this supersedes point (3) of the D023 decision (the 1- and 2-minute retry delays stay).
- **Alternativa descartada**: keep opening a session per run and raise the page count (the stream restarts at `msg_000001`, so it would re-read the same messages); keep the cursor in a field, Custom Setting or Custom Metadata (secret in data, already ruled out in D013); keep one Queueable per page with `pollAfterMs` delays (the org cuts the chain at depth 2 and every page would cost at least a minute); one job with callouts and DML interleaved (Salesforce forbids a callout after uncommitted DML).
- **Trade-off**: a run continues where the previous one stopped, so it stops repeating messages and 25 pages of 200 fit in 2 jobs; the cost is a new dependency (Platform Cache: a partition with allocated capacity, readable by any Apex in the org's namespace) and hidden state the screen has to explain (hence "Reiniciar sesión" and the detail). Without `pollAfterMs` pages are requested back to back, with no 10 s pause: we rely on the 429 retry and on cursors being idempotent. A non-retryable error mid-run no longer leaves a `Failed` job in Apex Jobs: it shows in the summary and the `WARN`. A restart re-reads from `msg_000001` and everything already stored counts as `yaExistentes`.
- **Riesgo / dependencia**: (1) the Platform Cache capacity of `nova-cdo` is not verified: if the org has none allocated, the partition deploy fails or the code falls back to "new session" and the original defect returns, with the notice on screen; the partition asks for 1 MB (`allocatedCapacity`) and may need adjusting. (2) The simulator may expire a session (409/410 is an assumption, D023): the saved cursor is cleared and a new session opened, with a re-read. (3) The heap, DML and CPU budget of 4000 messages per job was computed, not measured in the org: confirm with a 25-page run and tune `MAX_MENSAJES_POR_TRABAJO`. (4) Platform Cache holds no data in Apex tests, so tests use a map (`SesionSimulador.memoriaDePrueba`) and the real cache path is only checked in the org. (5) If the cache is flushed (platform restart, TTL) the next run silently opens a new session, visible only in the summary. (6) `Pagina.siguienteCursor` is still not filled when `hasMore=false`; if the simulator gave a useful cursor in that case, it could be saved instead of the last one read. (7) If saving the cursor fails (cache full, platform error) the run reports `cacheNoDisponible` and the next run opens a new session, i.e. it re-reads from the start. (8) After a 409/410 reopen, the saved cursor was cleared and a new session started: the next run starts from the new stream's beginning, not from where the old one was. (9) Page numbers are per run (and per job chain), not positions in the stream; they only label the `Rechazada` rows of discarded elements. (10) Replay after a restart relies on an UNCONFIRMED assumption: that a new session replays the same `source` + `messageId` so the identity dedupes it. If the simulator generates new ids per session, a restart would create new signals and interventions. Open question for the MDSS facilitator. (11) Platform Cache is not encrypted here; the cursor sits in it for up to 24 h readable by any Apex in the namespace (guarded only by a test that fails if another class calls `SesionSimulador.leerCursor`). Accepted risk: a cursor is a session handle for a simulator, not a credential, and the Bearer token never enters Apex.
- **Criterios de prueba**: `TelemetriaIngestaTest` (continues from the saved cursor without `POST /session`; with no cursor it opens a session; one job reads several pages and saves the next cursor; every callout sees the same DML count as before execution; an exhausted budget enqueues the continuation with no delay; `iniciar(..., true)` clears the cursor of that scenario and not another's, and `false` keeps it; a 410 on the saved cursor clears it and opens a new session; without cache it opens a new session and flags it; a mid-run failure writes what was read and retries the failed page; a non-retryable mid-run error does not throw; the cursor does not appear in the summary, the cache JSON, the screen detail or the exception message), `SesionSimuladorTest` (alphanumeric key, stable per parameters; save, read, clear; nothing throws without cache) and `IngestaControllerTest` (restart clears only with permission; the detail shows `yaExistentes`; an old summary is ignored; no cache means no detail). They fail if the saved cursor, the restart, the callout-before-DML order is removed or the cursor leaks.
- **Siguiente acción**: PR by John (Juan Diego reviews); `sf-deployer` validates the cache partition first (`--dry-run` with the partition and the classes) and confirms the capacity in Setup > Platform Cache; in `nova-cdo`, run `QA_200`/`MIXED` twice in a row with 25 pages and check that the second run brings new messages, then "Reiniciar sesión"; tell `sf-lwc-dev` about the change in `novaCasaActivosOperador` (ingestion panel).
